## Фаза 0 — Стабилизация

Мелкие, независимые, низкорисковые задачи. Делаются за один заход.

### 0.1 Домигрировать `admin_audit_log` — ✅ сделано

**Проблема.** Единственное оставшееся расхождение `schema:check`. Миграция
проверена локально, но её применение заблокировал классификатор auto-mode.

**Решение.** Применить вручную через Studio → SQL Editor, затем привести версию
в `supabase_migrations.schema_migrations` к `20260725233500`.

**Почему так.** Обходить блокировку через `execute_sql` нельзя. Ручное
применение через Studio — легитимный путь, а правка версии нужна, чтобы
история совпала с именем файла (см. Фазу 1).

### 0.2 Вынести `pg_trgm` из схемы `public` — ✅ сделано

**Проблема.** Advisor выдаёт WARN `extension_in_public`. Внесено миграцией
поиска: `create extension if not exists pg_trgm` без указания схемы.

**Решение.** Новая миграция: `alter extension pg_trgm set schema extensions;`
Проверить, что `search_catalog_products` и триггеры продолжают работать —
у них `set search_path = ''`, поэтому обращения к операторам trgm идут через
индексы, а не по имени; риск минимален, но прогнать `db reset` обязательно.

**Почему так.** Расширения в `public` засоряют пространство имён, доступное
через Data API. `extensions` — схема, которую Supabase создаёт именно для этого.

### 0.3 Гонка `next dev` и `tsc` — ✅ сделано

**Проблема.** Запущенный dev-сервер переписывает `.next/dev/types/routes.d.ts`,
`npm run typecheck` падает на рваном файле. Выглядит как поломка кода, ей не
являясь.

**Решение.** Исключить `.next/**` из `tsconfig.json` → `exclude`, оставив
типы маршрутов только для dev-режима. Альтернатива — не запускать `check`
параллельно с dev, но это не решение, а соглашение, которое будут нарушать.

**Почему так.** Проверка, падающая по внешней причине, обесценивает себя:
через неделю на её красный цвет перестанут смотреть.

## Фаза 1 — Фундамент схемы

Самая важная фаза. Пока она не сделана, `supabase db push` применять нельзя,
а значит любая работа со схемой остаётся ручной и хрупкой.

**Статус: шаг B выполнен, шаг C впереди.**

Сделано:

- локальная база признана достоверной копией прода — триггеры, политики и
  индексы совпали побайтово, функции разошлись ровно на `rls_auto_enable()`,
  принадлежащую облачной платформе;
- `20260810095928_baseline.sql` снят дампом, дополнен явным созданием `pg_trgm`
  в схеме `extensions` (дамп `--schema public` расширение не захватывает, а
  индексы на него ссылаются) и вставкой трёх Storage buckets;
- 21 прежняя миграция перенесена в `_archive/`, история сохранена в git;
- данные вынесены в `supabase/seed.sql`, `[db.seed]` включён — миграции
  описывают структуру, сиды наполняют локальную базу;
- история прода пересобрана: одна запись вместо девятнадцати;
- `supabase db reset` разворачивает всё с нуля, `schema:check` зелёный.

Попутно исправлен `scripts/check-supabase-schema.mjs`: его парсер не понимал
кавычки вокруг схемы (`"public"."products"` из `pg_dump` против рукописного
`public.products`) и читал только первый bucket из группового `INSERT`.

### Проблема

История миграций разошлась с репозиторием структурно, а не по недосмотру:

- локальные `0001`–`0011` против продовых timestamp-версий — совпадают только
  имена, для CLI это разные миграции;
- `0001_init` и `0002_grants` в истории прода отсутствуют вовсе — исходная схема
  заводилась мимо миграций;
- часть состояния создавалась через админку и Studio (типы техники,
  переименование «Тягач» → «Тонар»);
- миграции дописывались под уже готовый результат, поэтому из чистой базы набор
  не разворачивался ни разу.

`db push` в таком виде попытается накатить 13 уже применённых миграций:
`create table` поверх живых таблиц и повторный `seed_mock_data` поверх данных.

### Варианты

**Вариант A — `supabase migration repair`.** Привести версии в истории прода к
локальным именам файлов, для `0001`/`0002` вставить записи вручную.

Сохраняет гранулярную историю. Но оставляет 20 файлов со смесью `0001`-стиля и
timestamp-имён, не устраняет первопричину и не мешает следующему разъезду.

**Вариант B — новый baseline (рекомендуется).** Снять дамп текущей схемы прода
(`supabase db dump --schema public`), оформить как единственную стартовую
миграцию, старые файлы убрать в `supabase/migrations/_archive/`, историю на
проде пересобрать под новый baseline.

Даёт проверяемую точку отсчёта: `db reset` воспроизводит прод один в один.
Убирает класс имён `0001`–`0011` целиком. Гранулярная история не теряется —
она остаётся в git.

**Вариант C — baseline + декларативная схема (рекомендуется как цель).**
То же, что B, плюс переход на `supabase/schemas/`: описывается желаемое
состояние, миграции генерируются через `supabase db diff`.

Структурно исключает повторение: нельзя «дописать миграцию под факт», потому что
источником истины становится декларация, а не база. Это официальный современный
подход Supabase.

Ограничение: декларативные схемы не покрывают данные — сиды и разовые
преобразования остаются императивными миграциями. Это нормально и ожидаемо.

### Рекомендация

Идти **B → C**: сначала baseline (закрывает боль немедленно), затем перевод
структуры в `supabase/schemas/` (закрывает первопричину). Разделение на два шага
позволяет остановиться после B, если C окажется избыточным.

Это смена рабочего процесса, поэтому нужно ваше решение до начала работ.

### Как реализовать

1. `supabase db dump --linked --schema public -f supabase/migrations/<ts>_baseline.sql`
2. Сверить дамп с текущим `db reset` — расхождений быть не должно.
3. Пересобрать историю прода под baseline (`migration repair`).
4. `npm run schema:check` → зелёный.
5. Только после этого — шаг C: `supabase/schemas/`, генерация через `db diff`.

### 1.1 Защита от рецидива

Добавить в CI (`.github/workflows/ci.yml`) шаг `supabase db reset` на чистом
контейнере. Тогда неразворачиваемая миграция падает в PR, а не спустя месяцы.

Это то, что поймало бы все пять дефектов, найденных в этой сессии.

## Фаза 2 — Масштабируемость каталога

Бриф ориентирует на ~2000 товаров. В базе сейчас 15. Ниже — то, что сломается
при наполнении, причём **молча**.

### 2.1 Пагинация в админке

**Проблема.** `getAdminProducts` ([src/lib/admin/queries.ts](../src/lib/admin/queries.ts))
грузит весь каталог одним запросом. При `max_rows = 1000` в `config.toml` и
2000 товарах админка покажет половину, без ошибки.

**Решение.** Серверная пагинация через `.range()` плюс серверный поиск, по
образцу публичного `getProducts`.

**Почему offset, а не keyset.** Практики Supabase рекомендуют курсорную
пагинацию, и для публичного бесконечного списка это верно. Но админке нужен
переход на произвольную страницу, а объём ограничен ~2000 строк — на такой
глубине выигрыш keyset не окупает усложнения. Курсор оставить как путь на
будущее, если каталог вырастет на порядок.

**Связанный вопрос.** Список поддерживает drag-and-drop сортировку. При
постраничном выводе перетаскивание работает только внутри страницы. Нужно
решить: либо явный ввод порядкового номера, либо отдельный режим сортировки
без пагинации, либо перетаскивание только внутри подкатегории. Требует вашего
выбора — это UX-решение, а не техническое.

### 2.2 Массовые обновления вместо N+1

**Проблема.** `reorderProducts` шлёт отдельный UPDATE на каждый товар:

```ts
await Promise.all(
  orderedSlugs.map((slug, index) =>
    supabase.from("products").update({ order: index }).eq("slug", slug)),
);
```

При 2000 позициях — 2000 параллельных запросов к PostgREST. Исчерпает пул
соединений и почти наверняка упадёт. Транзакции нет: частичный сбой оставит
порядок в противоречивом состоянии.

Тот же паттерн у брендов, категорий, подкатегорий, `category_brands`, типов
техники и изображений товара — семь мест.

**Решение.** Одна RPC-функция, принимающая массив и обновляющая порядок
за один запрос в транзакции:

```sql
create function public.reorder_products(ordered_slugs text[])
returns void language sql security invoker set search_path = '' as $$
  update public.products as p
  set "order" = new_order.idx - 1
  from unnest(ordered_slugs) with ordinality as new_order(slug, idx)
  where p.slug = new_order.slug;
$$;
```

**Почему так.** Один round trip вместо N, атомарность из коробки, и это прямое
применение правила `data-n-plus-one` из практик Supabase.

### 2.3 Поиск: сделать индекс работающим

**Проблема.** Предикат в `search_catalog_products` построен на двойном
отрицании:

```sql
not exists (
  select 1 from unnest(string_to_array(query, ' ')) as word
  where product.search_text not like ('%' || word || '%')
)
```

Логически это «все слова присутствуют», но планировщик не может использовать
GIN-индекс trgm для отрицаемого `LIKE`. Advisor подтверждает:
`products_search_text_trgm_idx` ни разу не использован.

При 15 строках это незаметно. При 2000 — последовательный скан с проверкой
подстрок на каждой строке; README предлагает прогнать ещё и 5000.

**Решение.** Переписать на конъюнкцию положительных `LIKE`, которую trgm
индексирует:

```sql
and (
  normalized_query.value = ''
  or product.search_text like all (
    select '%' || word || '%'
    from unnest(string_to_array(normalized_query.value, ' ')) as word
  )
)
```

**Почему так.** Результат тот же, но предикат становится
index-friendly — минимальное изменение с максимальным эффектом.

### 2.4 Индексы под реальные запросы

Закрыть два INFO от advisor: неиндексированные внешние ключи
`category_brands.brand_slug` и `vehicle_hotspots.product_id`.

Остальные «неиспользуемые» индексы — новые, при 15 строках планировщик их
закономерно игнорирует. Оценивать повторно после наполнения каталога, не раньше.

## Фаза 3 — Наполнение и проверка под нагрузкой

### 3.1 Импорт из CSV/Excel

Пункт брифа, не реализован. Он же — предпосылка для всего остального: вручную
2000 позиций не завести.

**Реализация.** Server Action, разбор на сервере, батчевая вставка через
`upsert` пачками по 500 (правило `data-batch-inserts`), предпросмотр и отчёт об
ошибках построчно. Идемпотентность по `article` или `slug`, чтобы повторный
импорт обновлял, а не дублировал.

**Важно.** Аудит-триггеры из Фазы 0.1 сработают на каждую строку. При импорте
2000 товаров это 2000 записей аудита плюс столько же обновлений `search_text`
через триггеры. Проверить время импорта заранее; при необходимости отключать
триггеры на время массовой загрузки.

### 3.2 Нагрузочная проверка

Прогнать 2000 и 5000 товаров, замерить:

- p95 ответа каталога и поиска (бюджет — не более 1 с);
- LCP / CLS / INP против бюджетов README;
- время массового импорта и переупорядочивания.

Только после этого имеет смысл возвращаться к индексам (2.4).

### 3.3 Расхождение в данных

Тип техники `tyagach` называется на проде «Тонар», хотя слаг и комментарии в
коде говорят «Тягач». Подтвердить, что это осознанное переименование под
клиента, и привести комментарии в соответствие.

### 4.3 Развитие поиска

trgm — устойчивость к опечаткам.
