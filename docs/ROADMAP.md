## Фаза 1 — Фундамент схемы

Самая важная фаза. Пока она не сделана, `supabase db push` применять нельзя,
а значит любая работа со схемой остаётся ручной и хрупкой.

**Статус: шаги B и C выполнены.**

Шаг C — декларативные схемы. Структура описана в `supabase/schemas/prod.sql`,
`schema_paths` прописан в `config.toml`. Новый порядок работы: правится
декларация, миграция генерируется через `supabase db diff -f <name>`.

Перед принятием проверено эмпирически, а не по документации. Диф видит
изменение табличных привилегий: добавление `GRANT SELECT ... TO anon` в
декларацию он корректно вынес в миграцию. Это снимало главное опасение —
модель безопасности проекта держится на явных `GRANT`/`REVOKE`, и молчаливая
потеря `REVOKE` означала бы открытие таблицы через Data API.

Вне охвата дифа остаются: вставки данных, включая Storage buckets; привилегии
схемы и колонок; комментарии; `alter policy`. Всё это остаётся в миграциях.

Защита от рецидива оказалась частично готовой: CI уже разворачивал базу с нуля
через `supabase start`, но ни разу этого не сделал — коммиты не пушились, и
проверка простаивала. Добавлен шаг, сверяющий декларацию с миграциями, и
версия CLI в CI поднята до локальной.

Сделано:

- локальная база признана достоверной копией прода — триггеры, политики и
  индексы совпали побайтово, функции разошлись ровно на `rls_auto_enable()`,
  принадлежащую облачной платформе;
- `20260810095928_baseline.sql` снят дампом, дополнен явным созданием `pg_trgm`
  в схеме `extensions` (дамп `--schema public` расширение не захватывает, а
  индексы на него ссылаются) и вставкой трёх Storage buckets;
- 21 прежняя миграция перенесена в `_archive/`, история сохранена в git;
- данные вынесены в `supabase/seed.sql`, `[db.seed]` включён — миграции
  описывают структуру, сиды наполняют локальную базу;
- история прода пересобрана: одна запись вместо девятнадцати;
- `supabase db reset` разворачивает всё с нуля, `schema:check` зелёный.

Попутно исправлен `scripts/check-supabase-schema.mjs`: его парсер не понимал
кавычки вокруг схемы (`"public"."products"` из `pg_dump` против рукописного
`public.products`) и читал только первый bucket из группового `INSERT`.

### Проблема

История миграций разошлась с репозиторием структурно, а не по недосмотру:

- локальные `0001`–`0011` против продовых timestamp-версий — совпадают только
  имена, для CLI это разные миграции;
- `0001_init` и `0002_grants` в истории прода отсутствуют вовсе — исходная схема
  заводилась мимо миграций;
- часть состояния создавалась через админку и Studio (типы техники,
  переименование «Тягач» → «Тонар»);
- миграции дописывались под уже готовый результат, поэтому из чистой базы набор
  не разворачивался ни разу.

`db push` в таком виде попытается накатить 13 уже применённых миграций:
`create table` поверх живых таблиц и повторный `seed_mock_data` поверх данных.

### Варианты

**Вариант A — `supabase migration repair`.** Привести версии в истории прода к
локальным именам файлов, для `0001`/`0002` вставить записи вручную.

Сохраняет гранулярную историю. Но оставляет 20 файлов со смесью `0001`-стиля и
timestamp-имён, не устраняет первопричину и не мешает следующему разъезду.

**Вариант B — новый baseline (рекомендуется).** Снять дамп текущей схемы прода
(`supabase db dump --schema public`), оформить как единственную стартовую
миграцию, старые файлы убрать в `supabase/migrations/_archive/`, историю на
проде пересобрать под новый baseline.

Даёт проверяемую точку отсчёта: `db reset` воспроизводит прод один в один.
Убирает класс имён `0001`–`0011` целиком. Гранулярная история не теряется —
она остаётся в git.

**Вариант C — baseline + декларативная схема (рекомендуется как цель).**
То же, что B, плюс переход на `supabase/schemas/`: описывается желаемое
состояние, миграции генерируются через `supabase db diff`.

Структурно исключает повторение: нельзя «дописать миграцию под факт», потому что
источником истины становится декларация, а не база. Это официальный современный
подход Supabase.

Ограничение: декларативные схемы не покрывают данные — сиды и разовые
преобразования остаются императивными миграциями. Это нормально и ожидаемо.

### Рекомендация

Идти **B → C**: сначала baseline (закрывает боль немедленно), затем перевод
структуры в `supabase/schemas/` (закрывает первопричину). Разделение на два шага
позволяет остановиться после B, если C окажется избыточным.

Это смена рабочего процесса, поэтому нужно ваше решение до начала работ.

### Как реализовать

1. `supabase db dump --linked --schema public -f supabase/migrations/<ts>_baseline.sql`
2. Сверить дамп с текущим `db reset` — расхождений быть не должно.
3. Пересобрать историю прода под baseline (`migration repair`).
4. `npm run schema:check` → зелёный.
5. Только после этого — шаг C: `supabase/schemas/`, генерация через `db diff`.

### 1.1 Защита от рецидива

Добавить в CI (`.github/workflows/ci.yml`) шаг `supabase db reset` на чистом
контейнере. Тогда неразворачиваемая миграция падает в PR, а не спустя месяцы.

Это то, что поймало бы все пять дефектов, найденных в этой сессии.

## Фаза 2 — Масштабируемость каталога

Бриф ориентирует на ~2000 товаров. В базе сейчас 15. Ниже — то, что сломается
при наполнении, причём **молча**.

### 2.1 Пагинация в админке — ✅ сделано

Реализована через `.range()` с точным подсчётом, по 50 позиций. Перетаскивание
сохранено и более того — стало доступно там, где раньше отключалось.

Решение оказалось лучше обоих вариантов, которые обсуждались. `order` остался
**сквозным**: `reorder_products` переставляет товары внутри уже занятых ими
значений, а не нумерует подряд от нуля. Набор занятых слотов сохраняется,
товары вне выборки не сдвигаются. Поэтому перетаскивание корректно работает
на любом срезе — постраничном, отфильтрованном, найденном поиском, — и прежнее
ограничение «при активном поиске сортировка недоступна» снято.

**Проблема.** `getAdminProducts` ([src/lib/admin/queries.ts](../src/lib/admin/queries.ts))
грузит весь каталог одним запросом. При `max_rows = 1000` в `config.toml` и
2000 товарах админка покажет половину, без ошибки.

**Решение.** Серверная пагинация через `.range()` плюс серверный поиск, по
образцу публичного `getProducts`.

**Почему offset, а не keyset.** Практики Supabase рекомендуют курсорную
пагинацию, и для публичного бесконечного списка это верно. Но админке нужен
переход на произвольную страницу, а объём ограничен ~2000 строк — на такой
глубине выигрыш keyset не окупает усложнения. Курсор оставить как путь на
будущее, если каталог вырастет на порядок.

**Связанный вопрос.** Список поддерживает drag-and-drop сортировку. При
постраничном выводе перетаскивание работает только внутри страницы. Нужно
решить: либо явный ввод порядкового номера, либо отдельный режим сортировки
без пагинации, либо перетаскивание только внутри подкатегории. Требует вашего
выбора — это UX-решение, а не техническое.

### 2.2 Массовые обновления вместо N+1 — ✅ сделано

Семь RPC с `unnest(...) with ordinality`, один запрос в транзакции вместо
N round-trip'ов. — ✅ схема готова, код впереди

Семь RPC созданы. `reorder_products` устроен не так, как остальные: он не
перенумеровывает записи подряд, а перераспределяет уже занятые ими значения
`order`. Набор значений сохраняется, записи вне выборки не затрагиваются.

Это снимает вопрос, который иначе требовал выбора между сквозным порядком и
перетаскиванием: порядок остаётся глобальным, а сортировка мышью работает в
любом отфильтрованном или постраничном срезе. Побочно устраняется и нынешнее
ограничение «при активном поиске перетаскивание недоступно».

Осталось перевести на эти RPC вызовы в `src/lib/admin/actions.ts`.

### 2.2 (исходная формулировка)

**Проблема.** `reorderProducts` шлёт отдельный UPDATE на каждый товар:

```ts
await Promise.all(
  orderedSlugs.map((slug, index) =>
    supabase.from("products").update({ order: index }).eq("slug", slug)),
);
```

При 2000 позициях — 2000 параллельных запросов к PostgREST. Исчерпает пул
соединений и почти наверняка упадёт. Транзакции нет: частичный сбой оставит
порядок в противоречивом состоянии.

Тот же паттерн у брендов, категорий, подкатегорий, `category_brands`, типов
техники и изображений товара — семь мест.

**Решение.** Одна RPC-функция, принимающая массив и обновляющая порядок
за один запрос в транзакции:

```sql
create function public.reorder_products(ordered_slugs text[])
returns void language sql security invoker set search_path = '' as $$
  update public.products as p
  set "order" = new_order.idx - 1
  from unnest(ordered_slugs) with ordinality as new_order(slug, idx)
  where p.slug = new_order.slug;
$$;
```

**Почему так.** Один round trip вместо N, атомарность из коробки, и это прямое
применение правила `data-n-plus-one` из практик Supabase.

### 2.3 Поиск: сделать индекс работающим — ✅ сделано

С оговоркой по итогам замеров: `like all` сам по себе индексом **не
покрывается** — `EXPLAIN` даёт Seq Scan даже при `enable_seqscan = off`. Ни
эта форма, ни исходное двойное отрицание планировщику не годятся. Работает
только одиночный `LIKE`, поэтому предикат собран из двух частей: одиночный
`LIKE` по первому слову сужает выборку через GIN-индекс, а `like all`
доуточняет результат. Эквивалентность прежней формуле проверена на всех
словах и парах слов каталога. — ✅ схема готова

Первоначальное предложение из этого плана — заменить двойное отрицание на
`like all` — оказалось **недостаточным**. Проверка через `EXPLAIN` при
`enable_seqscan = off` показала, что `like all` не индексируется ни с
подзапросом, ни с массивом: планировщик в обоих случаях даёт Seq Scan.
Единственная форма, которую он сводит к GIN-индексу, — одиночный `LIKE`
или явная конъюнкция `LIKE`.

Итоговое решение: сужение по первому слову одиночным `LIKE` (даёт Index Cond)
плюс прежняя точная проверка «присутствуют все слова» как фильтр. Первое
условие отбирает надмножество, поэтому семантика не меняется.

Эквивалентность прежней формуле проверена на 52 словах и 52 парах слов
каталога — расхождений нет. Индексный план подтверждён и для параметра, а не
только для константы: функция с `SET search_path` не инлайнится, поэтому
проверялось именно через `PREPARE`.

### 2.3 (исходная формулировка)

**Проблема.** Предикат в `search_catalog_products` построен на двойном
отрицании:

```sql
not exists (
  select 1 from unnest(string_to_array(query, ' ')) as word
  where product.search_text not like ('%' || word || '%')
)
```

Логически это «все слова присутствуют», но планировщик не может использовать
GIN-индекс trgm для отрицаемого `LIKE`. Advisor подтверждает:
`products_search_text_trgm_idx` ни разу не использован.

При 15 строках это незаметно. При 2000 — последовательный скан с проверкой
подстрок на каждой строке; README предлагает прогнать ещё и 5000.

**Решение.** Переписать на конъюнкцию положительных `LIKE`, которую trgm
индексирует:

```sql
and (
  normalized_query.value = ''
  or product.search_text like all (
    select '%' || word || '%'
    from unnest(string_to_array(normalized_query.value, ' ')) as word
  )
)
```

**Почему так.** Результат тот же, но предикат становится
index-friendly — минимальное изменение с максимальным эффектом.

### 2.4 Индексы под реальные запросы — ✅ сделано

Два индекса на внешние ключи созданы. Оценка «неиспользуемых» индексов
проведена в 3.2 на 5012 товарах: индексы работают, планировщик выбирает
между составным и trgm по селективности запроса, удалению не подлежат.
Подробности и цифры — в разделе 3.2. — ✅ схема готова

Добавлены `category_brands_brand_slug_idx` и `vehicle_hotspots_product_id_idx`
— оба внешних ключа, отмеченных advisor'ом. Остальные «неиспользуемые» индексы

## Фаза 3 — Наполнение и проверка под нагрузкой

### 3.1 Импорт из CSV/Excel — ✅ сделано (CSV; XLSX — по решению пользователя, отложено)

CSV — своим RFC 4180 парсером, без зависимостей (кавычки, экранирование,
переводы строк внутри кавычек, BOM). XLSX не делался: спросил перед
добавлением зависимости, пользователь выбрал ограничиться CSV на первую
версию.

Двухшаговый поток: `previewProductImport` разбирает файл на сервере и валидирует
структурно (обязательные поля, существование категории/подкатегории/бренда/типа
техники) против справочников, загруженных одним запросом — без похода в БД на
каждую строку. `commitProductImport` вызывает RPC `import_products_batch`
пачками по 500.

Идемпотентность — через `article`, а не через `upsert` на уровне PostgREST:
`products.article` не имеет уникального ограничения в БД (в отличие от `slug`),
поэтому сопоставление со существующим товаром сделано explicit-обходом на
стороне TypeScript, с сохранением текущего `slug` найденного товара — импорт не
меняет URL уже опубликованных страниц.

Построчная изоляция ошибок — на уровне SQL, а не приложения: RPC оборачивает
каждую строку в собственный `EXCEPTION`-блок, одна некорректная строка не
откатывает весь батч. Найдено и исправлено тестированием до касания прода два
независимых бага (см. коммит слоя базы) — коллизия имени выходной колонки
`slug` с переменной PL/pgSQL и неверный синтаксис `with ordinality` для
характеристик.

Аудит-триггеры и `search_text` действительно сработают на каждую строку — это
и есть желаемое поведение: импортированные товары сразу находятся поиском,
операции сразу видны в аудите. Замер времени на реальном объёме — в 3.2.

### 3.2 Нагрузочная проверка — ✅ сделано (кроме Web Vitals)

Первый прогон на 2000 синтетических товарах вскрыл то, что ни одна прежняя
проверка не поймала: **создание и редактирование товара через настоящую
админку падало на проде**.

Причина — не хватало `GRANT EXECUTE` для `service_role` на
`refresh_product_search_text`. Функцию дёргает изнутри триггер обновления
`search_text`; вызов выполняется с правами того, кто сделал запись
(`SECURITY INVOKER`), то есть `service_role` — той самой роли, которую
`createAdminClient()` использует в реальном приложении. Без гранта — «permission
denied», `AFTER`-триггер прерывает всю операцию, весь `INSERT`/`UPDATE`
откатывается.

Не поймано раньше по методологической причине: все прежние проверки шли либо
через MCP `execute_sql`, либо через `psql -U postgres` — оба пути
привилегированные и `REVOKE` не задевают. Нагрузочный тест впервые прогнал
запись через `supabase-js` с `service_role`-ключом поверх PostgREST — тот же
путь, что и настоящее приложение, — и только так баг стал виден.

Исправлено `20260810201322_phase3_fix_search_text_permission.sql`, применено
на прод и подтверждено на обоих концах: локально через `supabase-js`, на
проде — прямым REST-запросом с секретным ключом (HTTP 204 вместо ошибки прав).
Триггерные функции-обёртки (`refresh_product_search_from_*`) грантов не
требуют — вызов триггера саму привилегию `EXECUTE` не проверяет, это
подтверждено эмпирически при диагностике.

#### Результаты после починки

Прогон на исправленной базе, локальный стек, через `supabase-js` поверх
PostgREST — тот же путь, что и приложение.

| Замер | 2000 товаров | 5012 товаров |
|---|---|---|
| Разбор + валидация CSV | 32 мс | 86 мс |
| Импорт в БД, батчи по 500 | 8,0 с | 29,0 с |
| p95 каталога, страница 1 | 55 мс | 128 мс |
| p95 поиска по частому слову | 56 мс | 132 мс |
| p95 поиска по алиасу бренда | 50 мс | 93 мс |
| p95 фильтра по категории | 35 мс | 53 мс |
| `reorder_products`, 24 позиции | 20 мс | 7 мс |
| `reorder_products`, 1000 позиций | 36 мс | 40 мс |

**Бюджет p95 ≤ 1 с выдержан с запасом примерно в 8 раз** даже на 5000 товарах,
то есть в 2,5 раза выше целевого объёма каталога.

Идемпотентность импорта подтверждена: повторный прогон дал «создано 3000,
обновлено 2000» — совпавшие по slug строки обновились, а не задублировались.

#### Индексы: вывод по 2.4

Первое впечатление было тревожным — `products_search_text_trgm_idx` показывал
ноль сканов даже на 5012 товарах. Разбор `EXPLAIN` показал, что тревога
ложная, а поведение правильное:

- **частое слово** — планировщик идёт по `products_published_order_idx` уже в
  нужном порядке и останавливается, набрав 24 строки (`LIMIT`). 0,35 мс,
  trgm-индекс не нужен и не был бы быстрее;
- **редкое слово** — `Bitmap Index Scan` именно по
  `products_search_text_trgm_idx`. 0,44 мс. Счётчик сканов подтверждён.

То есть планировщик выбирает стратегию под селективность запроса, и оба пути
укладываются в доли миллисекунды. Индексы нужны и удалению не подлежат.

Отдельно: предупреждения `unused_index` от advisor на **проде** неинформативны
— там 15 товаров и почти нет трафика, счётчики отражают отсутствие нагрузки,
а не бесполезность индексов. Возвращаться к ним имеет смысл только после
наполнения каталога и реального трафика.

#### Операционная находка: объём аудита

Цикл импорта (5000 созданий + 2000 обновлений + 5000 удалений) породил
**144 267 записей** в `admin_audit_log`: триггеры срабатывают на каждую строку
каждой связанной таблицы — характеристики, бренды, типы техники.

Само по себе это желаемое поведение, но при регулярных массовых загрузках
таблица аудита будет расти быстрее самого каталога. Перед вводом регулярного
импорта стоит решить, нужна ли политика хранения (например, чистка записей
старше N месяцев) — иначе аудит станет крупнейшей таблицей базы.

#### Web Vitals — измерить не удалось, и вот почему

Пользователь дал разрешение на запуск preview, попытка была сделана. Первый
замер на dev-сервере дал TTFB 4328 мс — и это число нужно было отбросить:
Next.js в dev компилирует страницы по требованию, метрика отражает компиляцию,
а не производительность.

Повторено правильно, на продакшен-сборке (`next start`, отдельный порт, чтобы
не мешать запущенному dev-серверу):

| Метрика | dev | production |
|---|---|---|
| TTFB | 4328 мс | **359 мс** |
| DOM complete | 4421 мс | 476 мс |
| Передано | — | 17 КБ |

Разница в 12 раз наглядно показывает, почему на dev-сборке производительность
мерить нельзя.

А вот **LCP, CLS и INP получить невозможно** — это ограничение среды, а не
недостаток усилий. Панель браузера не отображается на экране, страница не
компонует кадры (`document.visibilityState === "hidden"`, скриншот падает с
«the page is not compositing frames»). Без отрисовки метрик отрисовки не
существует: массив `paint` пуст, LCP не фиксируется ни через `getEntries`, ни
через `PerformanceObserver` с `buffered: true`. Побочный эффект того же —
`innerText` страницы почти пуст, хотя DOM корректен: элементы без раскладки
не отдают текст.

Проверено косвенно, тем, что не требует отрисовки: каталог отдаёт 15 карточек
товаров с корректными URL, маршруты админки защищены (307 на `/admin/login`),
страница входа отвечает 200.

Замер Web Vitals нужно делать инструментом, работающим в видимом браузере, —
Lighthouse, PageSpeed Insights или Vercel Speed Insights на реальном
развёртывании. Последнее уже упомянуто в README как штатный способ.

#### Страницы админки визуально не проверялись

`/admin/products` с пагинацией и `/admin/import` ни разу не открывались
человеком. Программно войти в админку я не стал сознательно: пароль пришлось
бы передать параметром инструмента, то есть записать боевой пароль в
транскрипт разговора. Проверка того не стоит — тем более что увидеть страницы
всё равно нельзя, панель не рисует.

Обе страницы проходят сборку и типизацию, маршруты зарегистрированы, защита
работает. Но первый реальный просмотр — за человеком.

Только после этого имеет смысл возвращаться к индексам (2.4).

### 4.2 Управление админ-пользователями — отложено по решению пользователя
