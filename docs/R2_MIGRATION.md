# Перенос публичных медиа AYPROM

## Состояние и границы

Это поддержка поэтапного переноса, а не подтверждение завершённой миграции.
По умолчанию сайт пишет в Supabase и использует прежние URL видео.
Для Cloudflare выбран аккаунт `5542d171bab5b5af3202e36e217f6ef9`
(`Kirsan.akmatbek@gmail.com's Account`), зона `81b63fd46108bbdab8a5c375cf9d09d6`.
Бакеты Standard: `ayprom-media-production` и `ayprom-media-test`.
Публичный адрес production: `https://media.ayprom-gidravlika.kg`.
Основной домен и www продолжают использовать текущий CNAME Vercel.

Перед переключением обязательны восстановленный Supabase, читаемая полная
резервная копия БД вне репозитория, ID действующего Vercel-деплоя и исходная
инвентаризация. JSONL миграции не заменяет полную резервную копию БД.
Существующий SEO-коммит также нужно учесть при выборе версии для публикации.

## Переменные и ключи

Сначала публикуется совместимая версия с `MEDIA_STORAGE_WRITE_TARGET=supabase`
и `NEXT_PUBLIC_HERO_MEDIA_SOURCE=supabase`. Для показа R2-адресов ей требуется
`NEXT_PUBLIC_MEDIA_BASE_URL`; это build-time настройка Next.js.

Production S3-ключ должен иметь права только на production-бакет. Тестовый ключ
и тестовая база используются отдельно. В браузер передаётся только публичный
адрес, S3-ключи остаются серверными. r2.dev не используется для production.

Перед записью в R2 создаётся отдельный **закрытый** Supabase bucket
`media-migration-journal`. В `MEDIA_STORAGE_JOURNAL_BUCKET` указывается его имя.
Это не bucket временных фотографий: очистка staging не должна удалять квитанции.
На первые 14 дней включается `MEDIA_STORAGE_DUAL_WRITE_SUPABASE=true`.
Успех загрузки возвращается только после обеих копий и закрытой квитанции.
Квитанция содержит ключ, оба адреса, размер и SHA-256; она не доказывает наличие
ссылки в БД — актуальные строки БД проверяются отдельно.

`MEDIA_STORAGE_RETAIN_OBJECTS=true` сохраняет физические объекты при замене и
удалении записей. Это режим по умолчанию, включая отсутствие переменной.
Логическое удаление в каталоге работает как прежде. Физическую очистку нельзя
включать до окончания наблюдения и отдельного решения об удалении резервов.

## Команды переноса

`npm run media:r2 -- --help` показывает параметры. Без флагов скрипт только
читает таблицы и записывает инвентаризацию JSONL вне репозитория. По умолчанию
каталог журнала находится в системном TEMP; перед работой нужно явно выбрать
долговечный внешний каталог, например `C:/Erkin/ayprom-backups/r2/`.

Пример копирования, без изменения ссылок:

```powershell
npm run media:r2 -- --scope=video --apply --copy-only --confirm-project-ref=acyoyvetcyqmwppfenau --confirm-r2-bucket=ayprom-media-production --journal=C:/Erkin/ayprom-backups/r2/video.jsonl
```

Параллельно копируются не более двух объектов. Каждый объект сохраняется также
локально по SHA-256 рядом с журналом. Существующая отличающаяся копия в R2 не
перезаписывается. Перед сменой ссылки проверяются содержимое через S3 и доступ
по публичному HTTPS-адресу. Ошибки дают ненулевой код выхода.

После видео выбирается `--scope=canary`: десять фотографий со всеми вариантами,
с приоритетом PNG/JPEG/WebP оригиналов, плюс категория, подкатегория и бренд.
Прозрачность PNG и наличие требуемых форматов нужно проверить по инвентаризации;
если формата нет в исходных данных, скрипт не создаёт искусственный пример.

Для изменения ссылок убирается `--copy-only` и добавляются
`--editing-paused --backup-confirmed`. Эти флаги — подтверждение уже выполненных
оператором условий, они сами не блокируют админку и не создают бэкап БД.
Перед этим прекращаются активные загрузки, сохраняется свежая инвентаризация.
Каждая ссылка обновляется только при совпадении текущего старого адреса (CAS).
Перед записью БД в журнал сбрасывается `db_update_intent`, после — результат.
Повторный запуск сверяется с текущими данными и проверенными R2-объектами.

## Откат и завершение

Для ссылок из миграции:

```powershell
npm run media:r2 -- --rollback --journal=C:/Erkin/ayprom-backups/r2/canary.jsonl --confirm-project-ref=acyoyvetcyqmwppfenau --editing-paused --backup-confirmed
```

Откат использует CAS и проверяет доступность исходного URL; последующие изменения
не перетираются. Видео откатывается отдельным build-time переключателем.
Для новых фото после перехода используется `--rollback-new` вместо `--rollback`,
с подтверждением проекта, R2-бакета, паузы редактирования и бэкапа. Скрипт читает
актуальные строки, закрытые квитанции и проверяет SHA-256 резервных файлов.
Удалённые строки не воссоздаются; изменённые ссылки защищает CAS. Файлы исходного
переноса пропускаются — они откатываются по исходному журналу. Этот сценарий ещё
нужно проверить на реальных тестовых данных до массового перехода. Старую базу
поверх действующей не восстанавливать.

До окончательного переключения остаются обязательными: полный бэкап, тесты
реальной загрузки/замены/сортировки/удаления в тестовом окружении, идемпотентный
повтор finalize, HTTP 206 видео, проверка OG/галерей/поиска, сценарий отката новых
фото, штатные gates и сверка опубликованного результата. После переключения —
наблюдение через сутки, три дня и две недели; это ещё не выполнено.
