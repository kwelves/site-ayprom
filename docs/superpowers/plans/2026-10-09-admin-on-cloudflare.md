# Админка на Cloudflare: полный перенос с прежним поведением и быстрым откликом

Дата: 2026-10-09. Решение владельца: перенести **все** функции админки с тем же поведением; правки
на публичном сайте могут появляться с задержкой; 95% действий админки должны ощущаться мгновенными
(~50 мс). Только локальная работа и staging; production, DNS и удалённые миграции боевой базы — отдельные
ворота.

## Архитектура (выбрана по факту кода)

Текущая админка Next состоит из ~23 тонких серверных страниц (1,1 тыс. строк), ~30 клиентских
компонентов (5,1 тыс.) и серверной логики: `actions.ts` (45 действий, 2,2 тыс. строк), `queries.ts`
(0,9 тыс.). Привязка серверного кода к Next минимальна: `cookies`, `headers`, `redirect`,
`revalidatePath/refresh`, Sentry, `server-only`. Компоненты уже вызывают действия как обычные
функции и сами делают оптимистичные обновления.

Поэтому вместо переписывания логики:

1. **Те же компоненты** собираются в одностраничное приложение (SPA, Vite) со статическими файлами в
   Cloudflare Static Assets; «страницы» — тонкие клиентские обёртки, получающие данные через API.
   Подмена только Next-зависимостей: `next/link`, `next/navigation`, `next/image` → маленькие шимы
   (History API).
2. **Те же серверные функции** (`actions.ts`, `queries.ts`) собираются в отдельный **admin Worker**
   с подменой Next-модулей (контекст запроса через AsyncLocalStorage; `redirect` превращается в ответ
   `{redirect}`, который клиент выполняет как переход SPA). Публичный Worker остаётся маленьким.
3. Единый RPC: `POST /api/admin/rpc/<имя>` для всех действий и запросов, сессия-cookie и Origin
   проверяются прежним кодом. `login`/смена пароля остаются на уже проверенном обработчике.
4. Тяжёлое, чего нет в Worker (Sharp, jsdom): обработка фото — внешний Node-процесс (очередь
   `product_media_jobs` уже есть); проверка SVG — совместимая замена на `@xmldom/xmldom`.
5. Публикация: после правки админка показывает «ожидает публикации» (код
   `product-publication-state.ts` уже есть), внешний сборщик публикует выпуск (отдельное решение о
   месте запуска: GitHub Actions / вручную).

## Скорость (~50 мс)

Сервер в Токио не даст 50 мс на сетевой запрос, поэтому отклик достигается на клиенте:
кэш данных в памяти (stale-while-revalidate), мгновенные переходы SPA, фильтры/поиск/сортировка
по уже загруженным спискам, оптимистичные записи с откатом при ошибке. Измеряется Playwright на
staging (клик → видимый результат), цель: p95 ≤ 50 мс для навигации, переключателей, фильтров,
сортировки, реордера, удаления/создания в списках. Тяжёлые операции (загрузка фото, commit импорта,
сохранение формы с проверкой конфликта) дают мгновенный отклик «сохраняется…» и не входят в 95%.

## Этапы (каждый: тесты RED→GREEN, локально и на staging, отчёт)

- M0 Основа: сборка SPA, шимы, RPC и admin Worker; доказательство на списке брендов (создать, переставить, удалить).
- M1 Товары: список/фильтры/пагинация, форма создания и правки, публикация/наличие, массовые действия, порядок, удаление.
- M2 Фото: загрузка (билет, staging, прогресс/повтор/отмена), режимы обработки, внешний процессор, порядок/масштаб/удаление.
- M3 Таксономия: бренды, категории, подкатегории, привязки категория–бренд, типы техники (CRUD, изображения, порядок).
- M4 «Спецтехника»: редактор точек, сохранить/отменить (CAS), поиск товаров для точки.
- M5 Импорт CSV, журнал аудита, безопасность (пароль).
- M6 Публикация после правки: «ожидает публикации», внешний сборщик, откат.
- M7 Скорость и проверка паритета: измерения, сравнение поведения с текущей админкой.

## Границы

Не менять боевую базу/домен/DNS/Vercel; не применять удалённые миграции к боевой базе; секреты только
в окружении процесса. Новые крупные зависимости — только по согласованию (Vite уже установлен
транзитивно через vitest).
