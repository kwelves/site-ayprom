## Что доказано на workerd

1. **Смена версии во время `finish` RPC** (backend меняет строку внутри обработчика `finish_admin_auth_attempt`):
   - хеш версии 2→3 и 3→4;
   - пустая строка с env-паролем → строка с хешем версии 2.

   Во всех трёх вход отказывает (`error=security`), cookie нет, `finish` вызван ровно один раз (`p_password_is_valid: true`). Запросы строго `begin → чтение → finish → чтение`; чтения вернули «старую» и «новую» версии. Защищённый запрос после такого входа сессии не находит.
2. **Стабильный вход:** cookie проверенной версии 3, `finish` один раз. Защищённый запрос с этой сессией — 200 (shell запрошен один раз). Backend меняет версию на 4 — следующий защищённый запрос: 302 `session=expired`, cookie очищается, shell не запрашивается.
3. **Сбой чтения credentials после `finish`** (backend отвечает 503 на чтение после `finish`): cookie нет, повторов и лишних чтений нет, `finish` один раз. Проверено на строке с хешем и на **пустой строке с env-паролем**. Если бы при сбое включался env fallback, второй вариант получил бы cookie версии 1. Первый вариант такой fallback сам по себе не ловит: версия хеша 3 не совпала бы с 1.
4. **Утечки и обращения:** за весь прогон ни одного запроса к `/auth/*`. Приватный ключ только в `apikey`, без `Authorization`, не в телах запросов. Ключа, паролей, хеша и cookie нет ни в одном ответе Worker и ни в перехваченном выводе Wrangler/workerd (проверка захвата: лог содержит записи о `/login`). Неверный пароль: `finish(false)` один раз, cookie нет.

## Отрицательный прогон (обнаруживают ли проверки сломанное поведение)

Просто зелёный новый тест не доказывает, что он что-то ловит: продукт уже защищён. Поэтому в production-код по очереди вносились контролируемые поломки, тест запускался, файл возвращался через `git checkout`/восстановление оригинала; итоговый `git status` показывает только мои файлы. Результат на изменённом коде — **тест падает** во всех пяти случаях:

| Поломка | Где ловится |
|---|---|
| M1. handler не сверяет проверенную версию с текущей | сценарий 1 (`hash 2→3`): cookie выдана |
| M2. cookie несёт текущую версию, сверки нет | сценарий 1 (`hash 2→3`): cookie выдана |
| M3. защищённый запрос не сверяет версию сессии | сценарий 2: после смены на 4 приходит 200 вместо 302 |
| M4. сбой чтения превращается в пустую строку (env fallback) | сценарий 3, вариант «пустая строка с env» (вариант с хешем M4 не ловит) |
| M5. `finish` вызывается дважды | сценарий 1: в списке запросов появляется второй `finish` |

На неизменённом коде тест проходит 1/1, повторно 2/2. Дефектов production-кода не обнаружено, патчей нет.

## Оставшееся окно гонки и ограничения

- **Окно после сверки.** Между сверкой текущей версии после `finish` и выдачей cookie версия может измениться ещё раз. Cookie несёт проверенную версию, поэтому такая сессия будет отклонена при следующем защищённом запросе (сценарий 2 доказывает механизм). Гарантия — «не выдать сессию новой версии по старому паролю», а не атомарность чтения БД и отправки cookie.
- **Что fixture не моделирует.** Смена версии между чтением состояния и проверкой пароля покрыта unit-тестами и предыдущим workerd-набором. Здесь окно — внутри `finish` RPC и после него.
- **Локальный workerd не применяет лимиты CPU.** Worker Free CPU для PBKDF2 на 600 000 итераций остаётся внешним gate; wall time не выдаётся за CPU.
- Backend — фикстура, а не настоящий PostgREST с таблицей `admin_credentials`; блокировки и порядок записи в реальной БД не проверялись.
- Подключение к `worker.ts` выполняет Codex; здесь его нет.
