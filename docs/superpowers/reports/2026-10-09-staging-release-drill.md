# Репетиция выпуска и отката на настоящем Cloudflare (staging), 2026-10-09

Только staging: тестовый Worker `ayprom-publication-staging` в аккаунте владельца и **копия**
базы `ayprom-staging` (бесплатная организация Supabase `kwelves`). Боевая база, боевой домен,
DNS и Vercel не менялись; боевую базу читали только публичным ключом, как посетитель.
`productionReady=false`, миграция не завершена.

## Что подтверждено на настоящем Cloudflare

Команда: `node scripts/cloudflare/staging-release-drill.mjs` (exit 0, 3 настоящие сборки).
- Первая выкладка Worker (`wrangler deploy`), затем **настоящие** неактивная загрузка версии,
  активация (`versions deploy`) и проверка страницы/поиска/браузером Chromium по адресу
  `https://ayprom-publication-staging.ayprom-migration.workers.dev`.
- Выпуск новой версии: `published`; страница, поиск и указатель каталога показывают одну редакцию.
- Сбой после активации (искусственно проваленная живая проверка) → **настоящий откат** через
  `wrangler rollback` → `failed_old_live`: сайт и указатель вернулись к прежней редакции,
  кандидат не виден.
- Копия каталога: 9 из 9 ответов поиска совпали с боевыми побайтно (88 товаров, фильтры, пустая выдача).

## Что нашла репетиция на настоящих данных (всё исправлено по TDD, ранее не видел ни один тест)

1. **У 70 из 88 боевых товаров пустое краткое описание** — проверка снимка требовала непустое.
   Теперь пустая строка допустима (не-строка отклоняется).
2. **7 товаров** категории `pto-shafts` (марки MAN/MAZ или без марки, а у категории ZF/Mercedes-Benz/Volvo)
   не имеют страницы; боевой сайт ведёт ссылку в `/catalog`. По решению владельца («оставить как сейчас»)
   сборщик повторяет это: `/product/<товар>` → 308 `/catalog`, без страницы и без записи в sitemap,
   вместо блокировки выпуска. Исправление данных остаётся желательной правкой в админке.
3. Тексты мета-тегов со слэшем («100л/мин», «14/15 ISO») принимались за ссылки на файлы и блокировали
   упаковку; теперь `content` считается ссылкой только если выглядит как адрес.
4. Wrangler 4.135 пишет перед записью команды служебную запись `wrangler-session` — порт ждал ровно одну.
5. Настоящий вывод загрузки сайта — 143 КБ (список файлов); порт отвергал вывод больше 64 КБ.
6. **Откат**: Cloudflare отказывает в `versions deploy` старой версии, если секрет `PUBLICATION_CAPABILITY`
   у версий разный (код 10220) — у каждого выпуска своё право. Откат теперь `wrangler rollback`
   (в CI сам подтверждает смену секрета) с проверкой по списку развёртываний.
Также: режим сборки `--staging-pinned` (снимок только для явно разрешённого удалённого staging-адреса,
не для боевого), параметры проверки товара в сборщике, подробные коды в отчёте сборки.

## Скорость (с этого компьютера, 30 запросов подряд, по настоящему интернету)

| Что | p50 | p95 | max |
| --- | --- | --- | --- |
| Главная | 30 мс | 37 мс | 46 мс |
| Каталог | 27 мс | 36 мс | 37 мс |
| Страница товара | 26 мс | 35 мс | 46 мс |
| **Поиск** (`/api/catalog/search?q=насос`) | **251 мс** | 268 мс | 359 мс |

Страницы укладываются в цель <200 мс с запасом. **Поиск — нет:** Worker обращается к базе
Supabase (Токио) на каждый запрос. Боевой сайт мои скрипты не пускает защита (403), поэтому
сравнение с Vercel не получено. Варианты ускорения (не реализованы, нужен выбор владельца):
(а) кэш в Cloudflare для ответов поиска — безопасен, потому что снимок выпуска неизменяем
(ключ кэша = выпуск + запрос); (б) Smart Placement — Worker ближе к базе; (в) предрассчитанный
индекс в статических файлах (самый быстрый, но самое большое изменение).

## Ограничения

- Это staging на копии данных и отдельном Worker, не боевой домен/DNS и не боевая база.
- Free-квоты Worker (CPU/запросы) не измерялись под нагрузкой.
- Админка и запись товаров (Task 5) по-прежнему не подключены; запись админки в боевую базу
  не проверялась.
- Токены Cloudflare/Supabase лежат в `%USERPROFILE%\.ayprom-secrets` вне репозитория; после
  работ их стоит отозвать/удалить.
