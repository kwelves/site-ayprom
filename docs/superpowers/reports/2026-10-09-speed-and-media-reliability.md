# Скорость сайта и надёжность картинок на Cloudflare staging, 2026-10-09

Только staging (тестовый Worker + копия базы). Боевой сайт, домен, DNS, боевая база не менялись.

## 1. «Битые» фото: причина и системная защита

Причина (скриншот владельца, блок «Спецтехника»): сборщик копировал из `public/` только файлы,
упомянутые в HTML-атрибутах. Пять фото техники упоминаются лишь внутри лениво загружаемых скриптов и
данных страницы — их не было в пакете, миниатюры показывали «битую картинку». Это касалось любых
картинок, названных только в скриптах.

Исправлено (TDD, `src/cloudflare/static-build/producer/public-assets.ts`):
- копируются **все** отслеживаемые Git файлы `public/`, чей полный путь встречается как литерал в HTML,
  данных страниц и JS-чанках (удалённые адреса вроде `https://cdn…/images/x.webp` не считаются);
- любой литерал, ведущий в известную папку `public/` с расширением файла, но не найденный среди
  отслеженных файлов, **останавливает сборку** (`missing_public_asset`) — битая картинка больше не
  доедет до сайта.

Устойчивость к сбоям сети (`ImageFallback`): фото, не загрузившееся ни как вариант, ни как мастер,
повторяется ещё дважды (через 0,5 с и 1,5 с, с параметром `_r=N` против кэша) и лишь потом заменяется
заглушкой. Проверено тестами; в аудите на живом сайте разовые сбои соединения восстанавливаются.

Проверка на живом staging (`scripts/cloudflare/staging-speed-audit.mjs`, настоящий Chromium, холодный кэш):
131 страница из sitemap, блок «Спецтехника» — 6 картинок, 0 битых после восстановления.

## 2. Переключение фото в миниатюрах (страница товара)

- Раньше: подгружалось только второе фото и только на «подтверждённом 4G» (в Safari/Firefox — никогда);
  остальные — при клике, отсюда ~1 с.
- Теперь: после показа первого фото в фоне подгружаются **все** остальные (кроме явных Save-Data/2G);
  плюс сервер кладёт в `<head>` подсказки `preload` для всех фото (`src/lib/preload-gallery-images.ts`),
  чтобы загрузка началась ещё до скриптов.
- Замер на живом staging (12 товаров, новый посетитель): через 1,5 с после открытия — **24–30 мс**
  в среднем, максимум 45–59 мс; клик сразу после загрузки страницы — 59–90 мс в среднем (догрузка идёт).
  Для самого первого мгновения после открытия 50 мс не гарантируется физически: файл ещё в пути.

## 3. Поиск

Каждый запрос шёл в базу Supabase (Токио): ~250 мс. Снимок выпуска неизменяем, поэтому ответ на запрос
внутри выпуска всегда один и тот же. `src/cloudflare/search-cache.ts`: ключ = выпуск + нормализованный
запрос; слой в памяти Worker (работает везде, в том числе на workers.dev) и слой Cloudflare Cache API
(только на своём домене; на workers.dev Cache API нет). Браузеру по-прежнему отдаётся `no-store`.
Замер: повторный запрос **16 мс** (p95 25 мс), первый уникальный запрос ~250–680 мс (поход в базу).
Вывод: быстро для частых запросов; первый уникальный запрос остаётся ~250 мс. Дальше — Smart Placement
или готовый индекс поиска в статических файлах (отдельное решение).

## 4. Переходы между страницами

Сайт на Cloudflare — готовые HTML-страницы, переход = загрузка страницы (30 мс с края сети + разбор и
запуск скриптов, у переходов на тёплом кэше 50–190 мс до готовности DOM). Добавлены правила
предзагрузки (`/speculationrules.json` + заголовок `Speculation-Rules`): браузеры на Chromium
предзагружают страницу при наведении/нажатии, админка, `/api/*` и `/product/*` исключены.
Подтверждено: заголовок и файл отдаются с правильным типом, браузер регистрирует правила (68 ссылок).
**Не подтверждено:** фактическая мгновенная активация — автоматизированный Chromium сам отключает
предзагрузку («PrerenderingDisabledByDevTools»). Safari/Firefox правила игнорируют. Реальный эффект
нужно смотреть вручную в Chrome на тестовом адресе.

## 5. Что нужно для настоящего переноса (решения владельца)

1. **Кто собирает и публикует сайт после правки в админке.** Публикация — внешний процесс (сборка
   Next ~7–10 мин + выпуск). На Vercel правка видна сразу; на Cloudflare без постоянного «сборщика»
   правка не попадёт на сайт. Варианты: GitHub Actions по сигналу из админки (правка видна через ~10 мин),
   сборка на компьютере владельца вручную, или иная схема. Это изменение поведения «1 в 1»: нужно решение.
2. **Запись из админки (Task 5)** в Worker не подключена: сейчас админка на Cloudflare только читает.
3. **Боевая база** не получила миграции снимков (нужны Worker и новый поиск). Применение удалённых
   миграций к боевой базе — только с отдельным разрешением владельца.
4. **Боевой Worker и домен**: создать боевой Worker с боевыми привязками (Supabase URL и ключи, R2),
   подключить домен `ayprom-gidravlika.kg` (зона уже в Cloudflare, тариф Free), DNS-план —
   `2026-10-08-dns-cutover-plan-draft.md`. Vercel остаётся запасным до окончания наблюдения.
5. Free-квоты Worker (запросов/CPU) под реальной нагрузкой не измерялись.
