# Админка на Cloudflare: что сделано и что осталось (2026-10-09)

Только локально и тестовая база (staging). Боевой сайт, домен, DNS и боевая база не менялись.

## Как устроено

- **Те же страницы и формы.** Админка собирается в одностраничное приложение из тех же файлов, что и
  сейчас (`src/app/admin/**/page.tsx`, `src/components/admin/*`). Вместо запросов в базу они вызывают
  «мост» `/api/admin/rpc/<имя>`.
- **Та же серверная логика.** Рабочий код `src/lib/admin/actions.ts` и `queries.ts` собирается в
  отдельный Worker (1,5 МБ, лимит бесплатного тарифа 3 МБ в сжатом виде). Next-зависимости заменены
  маленькими подменами (`src/cloudflare/admin-worker/shims`).
- **Тот же вход и сессия.** Тот же cookie `admin_session`, те же сообщения («Неверный пароль»,
  «Сессия завершена после смены пароля»), то же продление сессии.
- **Скорость.** Данные страниц лежат в памяти браузера: повторное открытие раздела — 15–60 мс
  (измерено в настоящем Chromium), удаление в списке — мгновенно (оптимистично, 5–11 мс).

## Проверено

- Все 21 страница админки открываются без ошибок (`scripts/cloudflare/admin-crawl.mjs`).
- Вход, неверный пароль, переходы, создание бренда с логотипом (PNG и SVG), удаление, вредоносный SVG
  отклоняется (`scripts/cloudflare/admin-smoke.mjs --write`).
- **Существующие e2e-тесты админки прогоняются на Cloudflare-версии**

  теста загрузки фото (см. ниже).
- `npm run check`: 2248 тестов зелёные.
- Проверка SVG без браузерной библиотеки (`src/cloudflare/admin-worker/svg`): те же списки разрешённого,
  что у DOMPurify (тест следит за расхождением), 22 настоящих SVG проекта сравнены с текущей проверкой,

## Очередь фото и публикация сайта (обновление 2026-10-11)

**Очередь фото (GitHub Actions).** Админка кладёт фото в промежуточное хранилище и ставит в очередь; `photo-queue.yml` запускается из админки (workflow_dispatch), обрабатывает WebP-копии и прикрепляет к товарам. Проверено на staging: фото появляется примерно через 26 секунд.

**Публикация после правки.** После любой правки админка будит `publish-site.yml`. Значок в админке: «Опубликовано» / «Ожидает публикации» / «Публикуется…» / «Ошибка публикации» (+ кнопка «Повторить», сам подталкивает через 3 минуты ожидания). Публикация собирает снимок каталога, проверяет его на закрытом адресе, переключает сайт, проверяет живой сайт и при сбое откатывается.

**Измерено на staging (Actions, публичный репозиторий):**
- сохранение правки: 3 с; значок «Ожидает публикации»: ~33 с; запуск публикации: ~70 с;
- правка видна на публичном staging-сайте: ~187 с (около 3 минут);
- один запуск публикации: 1–4 минуты (если публиковать нечего, ~1 минута).

**Исправлено по дороге:** на чистом сервере нет папки `dist` (проверка безопасности сборки требовала её), после отката Cloudflare даёт новый идентификатор деплоя (`publication-reconcile.mjs` его принимает, если версия и ревизия те же). Раннер теперь печатает журнал релиза при неудаче.

**Открыто:** один ранний запуск закончился `failed_old_live` (старая версия осталась живой, сайт не пострадал); причину тогда не записали, при повторе будет журнал. Токен GitHub для админки действует 90 дней: напомнить в январе 2027.

**Репозиторий публичный** (решение владельца 2026-10-11): минуты Actions безлимитны; в коде нет секретов, тестовые «ключи» в тестах — заведомо поддельные (`sb_secret_fakeNN`).

## Проверка остальных функций на staging (2026-10-12)

- **Импорт CSV**: был НЕ подключён к Cloudflare-админке (действия `previewProductImport`/`commitProductImport` лежат в отдельном файле). Подключено (виртуальный клиент + реестр Worker, лимит тела 8 МБ). Проверено: файл 1 строка — предпросмотр 1,7 с, импорт 1,4 с; предпросмотр 1500 строк — 1,7 с; импорт 600 строк — 5,3 с; тестовые товары удалены.
- **Журнал изменений**: 2545 записей, фильтры INSERT/UPDATE/DELETE, страницы — работают.
- **Спецтехника**: подпись точки сохраняется, после перезагрузки на месте, возврат работает, поиск товара для точки находит.
- **Смена пароля**: автоматически не проверялась (изменение защитных настроек, нужно сделать вручную владельцем на staging).
- **Найдена и исправлена серьёзная ошибка**: запросы админки на Cloudflare зависали (примерно каждый второй после «заражённого» экземпляра Worker). Причина: общий для запросов «обещанный» ответ про версию пароля; если запрос-автор отменён (браузер ушёл на другую страницу), обещание не завершается и все остальные ждут вечно. Теперь в Worker каждый запрос спрашивает базу сам, общий только готовый номер. Плюс таймаут 8 с и один повтор для чтений из базы. После правки: 50 из 50 запросов, 3 полных обхода 21 страницы без зависаний.
- Полная проверка проекта: 2291 тест, типы, линтер, цвета — зелёные.

**Смена пароля (проверено владельцем вручную на staging, 2026-10-12):** сначала упала с ошибкой `Pbkdf2 failed: iteration counts above 100000 are not supported`: Cloudflare Workers ограничивают PBKDF2 до 100 000 итераций, а прежний хеш был 600 000. Решение (вариант B, выбран владельцем): новые хеши `pbkdf2-sha256-chain:100000x6:…` — шесть проходов по 100 000, каждый подсолен результатом предыдущего (та же общая трудоёмкость, ~100 мс процессора на вход/смену). Старые хеши `pbkdf2-sha256:600000:…` проверяются только в Node (на Vercel); в Worker выдают явную ошибку. Владелец подтвердил: пароль сменился, подходит, старый не действует. **Перед переездом:** в реальной базе записи пароля нет (владелец не менял пароль на сайте), вход идёт по секрету `ADMIN_PASSWORD`; если запись появится до переезда — удалить её и положить текущий пароль в секрет Worker.
Замеры на Cloudflare (процессор на один вызов): PBKDF2 100 000 ≈ 16 мс, цепочка 6×100 000 ≈ 100 мс (P99 137 мс), scrypt N=16384 ≈ 38 мс; ошибок лимита CPU не было (тариф аккаунта нужно уточнить: на Free лимит 10 мс).
