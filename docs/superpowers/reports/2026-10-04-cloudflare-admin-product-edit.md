# Локальное редактирование товара в тонкой админке Cloudflare

Дата: 2026-10-04. Ветка `codex/claude-admin-product-edit` от `a024adf`.
Это локальная подготовка, не релиз: production Supabase/R2, Cloudflare account,
Vercel и DNS не затрагивались; Next/Vercel adapter не менялся.

## Что сделано

- **Приватное чтение одного товара** — `src/cloudflare/admin/product-detail-reader.ts`.
  Один GET в PostgREST по точному slug (`limit=2`: два ряда — отказ), только
  серверный ключ в заголовке, лимиты `requestAdminJson` (64 KiB, 10 с,
  redirect отклоняется). Возвращает все поля, которые заменяет
  `update_product_with_slug` (характеристики, бренды, типы техники,
  подкатегория), число точек витрины и `updated_at` **строкой как в базе**
  (микросекунды, без разбора в `Date`) — это значение для CAS.
- **`GET /api/admin/products/:slug`** — JSON только после проверки сессии и
  версии пароля; гость/отозванная сессия → 401, сбой проверки версии → 503,
  отсутствие товара → 404 `{"error":"not_found"}`, ошибка базы → 503 без деталей,
  `cache-control: no-store`. Прочие методы → 405.
- **HTML-форма без JavaScript** — `GET/POST /admin/products/:slug/edit`
  (`src/cloudflare/admin/product-edit-form.ts`). CSP без `script-src`, все
  значения экранированы, `expectedUpdatedAt` в скрытом поле. POST: Origin →
  сессия и версия → наличие порта записи → строгий разбор (известные ключи,
  без повторов, ≤ 64 KiB, ≤ 100 строк связей) → CAS-обновление. Успех — 303 на
  `?saved=1`; конфликт — 409 с введёнными значениями и ссылкой на актуальную
  версию (старая версия сохраняется, тихого повтора нет); 22023 — 400 с общим
  текстом; иное — 503 без текста базы. В списке товаров появилась ссылка «Открыть».
- **Порт записи**: SQLSTATE `22023` при HTTP 400 теперь `input_invalid`, а не
  «недоступно». Тест сверяет набор кодов с legacy `isIntentionalProductRpcError`.
- **`worker.ts`**: подключено только чтение. Запись (`updateProduct`) есть лишь в
  тестовой композиции `tests/support/product-edit-runtime-entry.ts`. В рабочем
  Worker форма показывается в `<fieldset disabled>` с пояснением, POST → 503,
  PUT → 404.

## Сверка с legacy Next adapter (не изменялся)

Как в `parseProductFormData`/`resolveProductEditSlug`: trim, пустые
необязательные поля → `null`, адрес через тот же `slugify`, строки
характеристик только при заполненных обеих частях, те же тексты ошибок
обязательных полей и адреса, `updated_at` передаётся без разбора. Отличия:
неизвестное `availability` отклоняется (legacy подставляет значение по
умолчанию); текст ошибок 22023 общий, без сообщения базы; бренды/типы техники
и категории вводятся slug-ами, а не выбором из справочников; фото не
редактируются. Переводы строк textarea (CRLF от браузера) нормализуются в LF,
поэтому сохранение без изменений не меняет описание.

## Проверки

- Unit/handler (RED → GREEN): reader 18, handler/форма 18, порт записи +2,
  wiring Worker +1 (RED без подключения → GREEN).
- Настоящий локальный workerd с HTTP-фикстурой: гость, чтение, экранирование,
  чужой Origin, сохранение, конфликт, oversized/500/redirect/битый JSON → 503,
  отзыв сессии; без изменений в handler тест падает (проверено).
- Изолированная Supabase (свой project id, порты 565xx) + реальный PostgREST +
  два workerd: 12/12, `cleanup: true` —
  `scripts/cloudflare/local-product-edit-contract.mjs`. Доказано: точная строка
  `updated_at` с микросекундами из API совпадает с базой; сохранение формы
  переименовывает товар без потери связей и описания; устаревшая форма → 409
  без записи; реальный PostgREST отдаёт 22023 как HTTP 400 → понятная ошибка;
  рабочий `worker.ts` читает, но не пишет; после смены версии пароля старая
  cookie ничего не читает и не пишет; публичный ключ черновик не видит.
- `npm run check`: lint, typecheck, check:colors, 1762 passed / 4 skipped.
- Локальный `wrangler deploy --dry-run` (без upload): Worker 70.75 → 96.48 KiB,
  gzip 16.42 → 22.47 KiB; рост в основном из-за кириллицы формы, которую
  esbuild экранирует как `\uXXXX`.

## Не сделано и не доказано

- Нет механизма обновления статических страниц после правки товара — поэтому
  запись не подключена в `worker.ts`, а админка не готова к публикации.
- Нет проверки в настоящем браузере (форма отправлялась HTTP-запросами,
  сериализованными как у браузера без JS через parse5).
- Create/delete/publish/bulk/фото/импорт, audit (ADM-09), удалённый staging и
  Worker Free CPU не проверялись. ADM-05 повышен только до PARTIAL.

## Дополнение: настоящий браузер (2026-10-04)

После исходного отчёта локальный контракт расширен проверкой Chromium с
отключённым JavaScript. Браузер входит через `/admin/login`, открывает форму
товара, сохраняет новое название и получает 303 с `?saved=1`; данные в отдельной
тестовой Supabase подтверждают изменение без потери описания. Вторая, заранее
открытая вкладка пытается сохранить устаревшую версию и получает 409; запись в
базе остаётся прежней. Общий локальный сценарий прошёл 13/13 проверок с
`cleanup: true`. Это проверяет тестовую композицию с портом записи, а не включает
её в рабочем `worker.ts`: сохранение в нём по-прежнему отключено до безопасного
обновления опубликованных статических страниц. Производственный сайт и сервисы
не менялись.
