# Однократный вход обработчика фото (2026-10-03)

Статус: **локально, без scheduler и без production-запуска**.

`runNextPhotoJob` в `src/cloudflare/media/product-photo-job-runner.mjs` соединяет закрытую очередь с уже существующим Node/Sharp runner. Он проверяет наличие всех портов хранения и базы, публичный HTTPS-адрес и длительность аренды до получения задания. Затем берёт не более одного задания; пустая очередь возвращает `null`, а ошибка чтения очереди превращается в фиксированную ошибку без текста backend. Успешное задание передаётся существующему runner, который сверяет байты исходника, сохраняет три объекта, проверяет HEAD и только после этого подтверждает публикацию в БД.

TDD: четыре новых теста упали до реализации из-за отсутствующей функции, пять прежних остались зелёными. После минимальной реализации весь файл — 9/9; локальный сквозной тест переведён на новый вход и проверяет успех, повреждённый исходник и несовпадающий HEAD — 3/3. Конфигурация не содержит паролей или ключей и не читает переменные окружения сама.

Проверки: `npm run check` завершился с кодом 0 — lint, typecheck, colors и 1700 прошедших тестов (4 пропущены). `npm run build` не запускался: Node-only обработчик не входит в Next-сборку, а в этом worktree нет `.env.local`; предыдущую сборку не выдаём за новую. Сообщение jsdom о неподдерживаемой навигации не является падением теста.

Это ещё не самостоятельная служба: нет расписания, deployment, Worker-upload или живой БД/R2. Реальные ключи не применялись. Нельзя считать админскую загрузку фото готовой, пока не пройдут итоговая миграция в изолированном Supabase, test R2 и end-to-end upload из защищённой админки. [Рекомендации Supabase по ключам](https://supabase.com/docs/guides/getting-started/api-keys) требуют держать секретные ключи только на серверной стороне.
