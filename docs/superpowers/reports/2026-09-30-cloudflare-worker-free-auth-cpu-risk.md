# Риск CPU для входа администратора на Workers Free

Проверка локальная, без аккаунта Cloudflare, deploy, production-данных или изменения способа авторизации. Продуктовый Worker не менялся.

## Проверяемый факт

Текущая схема пароля использует PBKDF2-SHA256 с 600 000 итераций. Локальный `workerd` (закреплённый Wrangler 4.135.0) выполняет её корректно, но выполнение дорогое. В новом test-only runtime probe после одного прогрева на каждый режим получены шесть последовательных измерений в каждом из двух прогонов:

| Операция | Workerd wall, первый / повторный прогон | HTTP round-trip, первый / повторный прогон |
|---|---:|---:|
| Сравнение с env-паролем через SHA-256 | 0 / 0 мс (таймер округлил короткую операцию) | 12,61 / 14,10 мс |
| Проверка существующего PBKDF2 hash | 338 / 506 мс | 345,86 / 531,23 мс |
| Создание нового PBKDF2 hash | 455 / 591 мс | 469,21 / 616,69 мс |

Повторный прогон шёл одновременно с линтером, поэтому цифры выше; тест фиксирует порядок величины, не обещает стабильный benchmark каждой машины.

Воспроизведение: `npx vitest run tests/cloudflare-admin-crypto-timing-runtime.test.ts --maxWorkers=2 --silent=false --reporter=verbose`. Fixture не принимает пароль из запроса и отдаёт только boolean и длительность; hash и пароль в ответ не попадают. Порогов времени в тесте нет, чтобы не превращать различия машин в ложный отказ.

**Это wall time, а не измеренный Cloudflare CPU time.** Локальный `wrangler dev` не применяет удалённые лимиты, и время может отличаться на других машинах. Поэтому тест не доказывает, что конкретный запрос превысит квоту Cloudflare Free. Он показывает существенный риск, который нельзя снять успешным локальным входом.

## Внешний лимит и решение

По [официальным лимитам Workers](https://developers.cloudflare.com/workers/platform/limits/) Free допускает 10 мс CPU на HTTP-запрос; ожидание сетевых запросов не считается CPU. [Документация таймеров](https://developers.cloudflare.com/workers/runtime-apis/performance/) разрешает измерять локальную длительность через `performance.now()`, но не приравнивает её к фактическому счётчику CPU в аккаунте. [Документация Wrangler](https://developers.cloudflare.com/workers/wrangler/configuration/) прямо указывает, что локальная разработка не применяет лимиты сети Cloudflare.

Перед объявлением admin parity нужна разрешённая владельцем изолированная удалённая проверка без production DNS и данных: типовые успешный/неверный входы, несколько последовательных попыток и наблюдение фактического `cpuTime`/`exceededCpu`. До неё Worker Free для PBKDF2 остаётся непроверенным gate. Не уменьшать 600 000 итераций и не менять алгоритм только ради квоты. Если gate не пройдёт, отдельно согласовать Workers Paid либо вынесение проверки пароля во внешний доверенный compute; это архитектурный выбор, не автоматическая правка.
