# AYPROM: локальный пакет для проверки admin-auth вместе с публичным сайтом

Дата: 2026-09-29
Статус: подтверждено владельцем; локальная реализация проверена 2026-09-30 (см. отчёт `2026-09-30-cloudflare-admin-preview-package.md`)
Среда: только локальная; не production-релиз

## Цель и границы

Проверить в **одном локальном пакете**, что готовые публичные страницы продолжают работать через Cloudflare Static Assets, а `/admin` и `/api/admin/*` проходят через уже реализованный тонкий Worker и не обходят проверку сессии. Пользователь подтвердил отдельный `admin-preview` пакет вместо безусловного изменения существующего публичного пакета.

Успех здесь означает воспроизводимую локальную проверку маршрутов, входа и выхода на отдельной тестовой Supabase. Он **не** означает готовность настоящей админки или разрешение на публикацию. Ни push, ни deploy, ни изменение DNS/Vercel/production Supabase/R2 не входят в этот этап. Действующий Next/Vercel login и публичный поиск остаются прежними.

## Текущее состояние

- `scripts/cloudflare/package-worker-assets-lib.mjs` упаковывает проверенный `dist/staging/<run>/site`, создаёт Worker из `alias-worker-entry.mjs` и помечает локально целостный публичный пакет как `ready: true`.
- Конфигурация такого пакета запускает Worker перед `/api/*` и `/product/*`, но не содержит привязку `ASSETS` и правила для `/admin`. Поэтому auth-handler, хотя и входит в исходный Worker, не имеет нужного маршрута и HTML-оболочки в объединённом пакете.
- Отдельный `wrangler.admin-local.jsonc` и `fixtures/cloudflare-admin-assets` уже доказали login, cookie gate, logout, ошибки и браузер без JavaScript. Это только тестовая пустая оболочка, не CRUD.
- Cloudflare по умолчанию отдаёт совпавший Static Asset до вызова Worker. Для закрытых адресов требуется выборочный `assets.run_worker_first`: [документация Cloudflare](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/).

## Выбранная схема

Новый явный режим упаковки создаёт **отдельную новую папку** `dist/worker-packages/<уникальное-имя-admin-preview>` из уже проверенного публичного staging. Существующий публичный CLI, его конфигурация, результат и смысл `ready: true` не меняются.

Режим preview повторно использует существующие проверки staging, границ путей, секретов, размеров, содержимого и сборку Worker через локальный Wrangler dry-run. Он добавляет к копии публичного `site/` **только два отслеживаемых Git файла** из фиксированного allowlist:

- `fixtures/cloudflare-admin-assets/admin/login.html` → `site/admin/login.html`;
- `fixtures/cloudflare-admin-assets/admin/index.html` → `site/admin/index.html`.

Путь к произвольной admin-папке не принимается. Если в публичном staging уже есть `admin`-файл или каталог, коллизия отклоняется до создания output. Symlink/junction на пути источника, неподдерживаемый тип файла, карта исходников, потенциальный секрет, превышение общего лимита файлов или байт и любой неуспешный отчёт staging также дают отказ до записи output. Проверка выполняется для объединённого содержимого, а не отдельно для двух групп. Сбой оставляет исходный staging и существующие пакеты без изменений.

В preview `wrangler.jsonc` задаёт `assets.directory: "site"`, `assets.binding: "ASSETS"`, `html_handling: "drop-trailing-slash"`, `not_found_handling: "404-page"` и `run_worker_first: ["/api/*", "/product/*", "/admin", "/admin/*"]`. Публичные страницы остаются asset-first. Код Worker по-прежнему использует существующий admin-handler; новая копия алгоритма входа не создаётся. Прямые `/admin/login.html` и `/admin/index.html` должны быть отклонены Worker, даже если физические файлы лежат в `site/`.

## Маркер готовности и секреты

Манифест preview явно содержит `kind: "admin-preview"`, `previewReady: true`, `productionReady: false`, `ready: false` и перечень **имён** обязательных bindings: `ASSETS`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `ADMIN_SUPABASE_KEY`, `ADMIN_AUTH_EMAIL`, `ADMIN_AUTH_USER_ID`, `ADMIN_COOKIE_HMAC_KEY`. Это различает успех локального изготовления от существующего публичного `ready: true` и не даёт простому потребителю поля `ready` принять тестовую админку за релиз. Отдельный preview CLI возвращает exit 0 только при `previewReady: true`; штатный публичный CLI не меняется. В логах и манифесте нет пароля, значений ключей, IP, auth-токенов или исходного HTML.

Пакет содержит только **имена** привязок/секретов, но не их значения. Для локального smoke-test значения поступают из отдельной временной конфигурации вне пакета, создаваемой только для изолированной Supabase; она удаляется после теста. При отсутствии обязательных admin bindings Worker закрывает `/admin` с 503, не открывая тестовую оболочку, а публичный health/search остаются доступными. Никаких production-значений или переноса действующего `ADMIN_PASSWORD` нет.

## Проверки и критерии приёмки

Реализация идёт через RED → GREEN тесты. Доказательства включают:

1. Обычный публичный пакет создаётся как раньше и не получает admin-файлы, `ASSETS` или новые правила. Preview создаётся только по отдельной явной команде и не меняет `dist/site`.
2. Позитивный пакет имеет оба разрешённых HTML, корректный Worker/config и манифест с `productionReady: false`; в пакете нет source map, служебного `meta` или значений секретов.
3. Отрицательные тесты для отсутствующего/отрицательного отчёта, недопустимого output, коллизии `admin/`, symlink/junction, неподдерживаемого файла, секрета и превышения общего бюджета подтверждают отказ **до** создания пакета. Чужой output не удаляется.
4. Настоящий локальный workerd с preview-пакетом отдаёт публичные `/`, health, поиск и product alias по прежним контрактам; гостю не отдаёт `/admin` и прямые HTML-файлы; проверяет login/logout, неверный пароль, отсутствие/подделку/истечение cookie, изменение версии и отказ backend. Браузерный сценарий проходит без JavaScript. Тестовая Supabase изолирована и убирается после проверки.
5. Выполняются целевые и полные тесты, lint/typecheck, локальные `next build` и Wrangler dry-run, проверка размера Worker, `git diff --check`, Graphify и локальный Git checkpoint. Результаты и ограничения фиксируются в отчёте; ничего не публикуется.

## За пределами этапа

Этот пакет не переносит реальные страницы админки, CRUD, загрузку файлов, смену пароля, production credentials и наблюдаемость удалённого Worker. Тестовая оболочка не содержит приватных данных. Отдельные обязательные gates до production: полноценный admin API/UI, изолированный удалённый staging с настоящими bindings и измерением Worker Free CPU, проверка rollback на Vercel и отдельное согласование cutover.
