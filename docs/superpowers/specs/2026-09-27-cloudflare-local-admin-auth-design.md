# Локальный прототип входа в админку через thin Worker

Дата: 2026-09-27. Статус: спецификация для просмотра владельцем проекта; реализация не начата.

## Цель и граница

Проверить в изолированном локальном окружении, что статическая форма входа, тонкий Cloudflare Worker и Supabase Auth могут сохранить привычный вход с одним паролем и контракт сессии AYPROM. Успех этого прототипа **не** означает готовность всей админки или разрешение на публикацию.

В рамках прототипа не меняются production Supabase, действующий пароль, Vercel login, DNS, R2 и общий локальный Supabase. Нет push или deploy. Не переносятся CRUD, загрузка фото, импорт, смена пароля и публикация каталога. Для будущего cutover они остаются отдельными обязательными воротами.

## Фактическая отправная точка

- Текущий выбранный пакет Static Assets + thin Worker не содержит `/admin`: локальный workerd отвечает 404 на `/admin` и `/admin/login` (`docs/superpowers/reports/2026-09-27-cloudflare-admin-package-gap.md`). Исторический full-vinext spike не доказывает работу выбранной архитектуры.
- Legacy Next использует Server Action `login`, атомарные `begin_admin_auth_attempt`/`finish_admin_auth_attempt`, HMAC-cookie `admin_session` и проверку `session_version`. Если `admin_credentials` пуста, пароль сравнивается с `ADMIN_PASSWORD`; PBKDF2-хеш используется после смены пароля. Прототип не должен предполагать, что production уже использует Supabase Auth.
- У Workers Free лимит CPU 10 мс на HTTP-запрос. Ожидание внешнего `fetch` не учитывается как CPU, но фактический запас всё равно придётся измерить на отдельном удалённом staging до cutover: <https://developers.cloudflare.com/workers/platform/limits/>.

## Маршруты и компоненты

1. `/admin/login` — безопасная статическая форма с одним полем пароля. Её `POST` направляется на `/api/admin/login`, а не на Next Server Action. Форма работает и без JavaScript. В HTML/JS нет email тестовой учётной записи, пароля, service-role, session secret или данных администратора. Worker отдаёт статический шаблон через `ASSETS` и для разрешённых `error`/`retry` параметров добавляет только заранее заданный безопасный текст ошибки; это сохраняет сообщение после redirect без JavaScript. Ответ login не кэшируется.
2. `/api/admin/login` — Worker-only обработчик. Он принимает ограниченное по размеру `application/x-www-form-urlencoded` тело, требует совпадения `Origin` с origin запроса и отклоняет остальные методы/типы тела. Порядок: атомарная бронь попытки → удалённая проверка пароля → фиксация результата брони → выпуск app-cookie. Успех даёт `303` на `/admin`; неверный пароль — `303` на `/admin/login?error=1`; ограничение — `303` с `error=rate` и безопасным `retry`; сбой защиты — `303` с `error=security`. При сбое verifier бронь завершается как неудачная, если RPC доступен; при любом обязательном сбое cookie не выдаётся. Если `Origin` неверен или тело неприемлемо, Worker возвращает ошибку без проверки пароля.
3. Для проверки пароля Worker обращается к **отдельной локальной** учётной записи Supabase Auth с фиксированным email, известным только серверу. Supabase Auth поддерживает вход по email и паролю: <https://supabase.com/docs/guides/auth/passwords>. Worker принимает результат только если `user.id` равен настроенному фиксированному admin ID; произвольный успешно вошедший пользователь не становится администратором. Auth access/refresh tokens не передаются браузеру, не пишутся в логи и не используются как app-session cookie. Запросы не разделяют mutable Auth session между вызовами Worker и не сохраняют Auth tokens в глобальном состоянии. Этот verifier — локальный прототип, не миграция действующего пароля.
4. `/api/admin/logout` — `POST` с проверкой same-origin; удаляет `admin_session` и перенаправляет на `/admin/login`. Остальные `/api/admin/*` не реализуются этим срезом и не должны давать доступ к данным.
5. `/admin` и `/admin/*` — Worker-first. `/admin/login` доступен гостю; остальные маршруты без корректной cookie перенаправляют на login. После проверки HMAC, срока и текущей версии учётных данных Worker отдаёт только статическую тестовую оболочку через `ASSETS`; она не содержит приватных данных. Неизвестные admin-пути не превращаются в доступ к защищённым данным. Публичные страницы остаются asset-first, `/api/*` — Worker-first. Возможность выборочного `run_worker_first` и `ASSETS` binding описана в <https://developers.cloudflare.com/workers/static-assets/binding/>.

## Сессия и секреты

- Выделить платформенно-нейтральный код HMAC-cookie с явной передачей секрета/времени. Legacy Next adapter сохраняет прежний формат и поведение; Worker adapter использует тот же код. Тесты подтверждают взаимное чтение токенов и байтовую совместимость при фиксированном времени и секрете.
- Сохранить `HttpOnly`, `SameSite=Lax`, `Path=/`, срок 7 дней, refresh в последний час и абсолютный предел 30 дней. `Secure` обязателен на HTTPS; локальный HTTP проверяется отдельно, не ослабляя правило для будущего HTTPS.
- При отсутствии строки `admin_credentials` версия равна 1. Другие ошибки чтения версии закрывают доступ. Кратковременный кэш версии не должен позволять старой сессии жить дольше legacy-окна 10 секунд после изменения версии. В первом срезе смена версии симулируется только в изолированной тестовой БД, не через форму смены пароля.
- Для admin rate-limit RPC и чтения версии нужен привилегированный **серверный** ключ, существующие функции уже запрещены `anon`/`authenticated`. Ключ доступен только Worker adapter, не публичному поиску, статическим файлам или браузеру. Публичный `/api/catalog/search` остаётся на publishable key. Ни один секрет не попадает в отчёты тестов, URL или ошибки.
- Ключ ограничения попыток берётся из доверенного адреса входящего запроса; произвольный `X-Forwarded-For` клиента не должен обходить лимит. Ошибки Auth, RPC и проверки сессии обрабатываются fail-closed. Защищённые ответы и redirects не кэшируются публично.

## Проверки и критерии приёмки

Сначала TDD contract tests на чистых обработчиках: корректный/неверный пароль и точные redirect/status, чужой admin ID, параллельные попытки, RPC-ошибка до/после verifier, неверный `Origin`, неподдерживаемый метод/тип/размер тела, отсутствующая/поддельная/просроченная cookie, refresh и устаревшая `session_version`. Проверить, что ошибка никогда не выдаёт cookie или секрет, чужие/неизвестные query-параметры не внедряются в HTML и публичный поиск не получает admin-ключ.

Затем запустить **отдельный** локальный Supabase-проект в Docker с собственными портами/данными и тестовой Auth identity. До запуска проверить отсутствие конфликтов; не стартовать, не останавливать и не очищать общий стек. Только в этом изолированном проекте разрешены создание тестового пользователя, вызовы rate-limit RPC и изменение тестовой версии сессии. Повторить контракт через настоящий локальный workerd и браузер: вход без JS, неправильный пароль, лимит попыток, перезагрузка страницы, переход гостя, выход, прямые запросы к `/admin` и API, ошибки backend. Тесты должны убирать только собственные временные ресурсы.

Для данного среза локальные `npm run check`, `npm run build`, Wrangler dry-run, workerd и browser smoke должны пройти; Graphify обновляется до локального Git-чекпоинта. Полный свежий static producer/package не объявляется admin-ready до включения оболочки в manifest, проверки всех admin URL и отдельной проверки упаковки без секретов. CPU Free не признаётся доказанным по локальному workerd.

## Отдельные решения перед production

Требуются новая проверка и отдельное согласование: перенос действующего пароля из `ADMIN_PASSWORD` на удалённый verifier с сохранением Vercel rollback, реальная смена пароля и инвалидирование сессий, перенос всех admin CRUD/API, тестовые R2-медиа, удалённый staging с реальными bindings и измерением CPU, затем DNS cutover. Ни один из этих шагов не выполняется в рамках прототипа.
