# AYPROM: согласованная публикация каталога

Дата: 2026-10-05. Статус: утверждена владельцем; код и production этим документом не меняются.

## Цель и границы

Администратор может сохранить правку товара и увидеть её в админке, но посетитель видит только последнюю успешно проверенную и опубликованную версию. Страницы, поиск, карточки, фильтры, изображения и канонические ссылки относятся к одной версии. Сбой сборки или публикации оставляет старую версию доступной. Откат возвращает и страницы, и результаты поиска к прежней версии. Хостинг остаётся на бесплатной архитектуре Cloudflare Static Assets + тонкий Worker + Supabase + R2; Vercel сохраняется как проверенный резервный источник, но не как постоянный публичный хостинг.

Этот дизайн описывает подсистему публикации, без которой нельзя безопасно подключить запись из Cloudflare-админки. Он не объявляет готовыми остальные функции админки, медиа-процессор, DNS-переключение или саму миграцию.

## Почему текущего механизма недостаточно

Сейчас `content_revision` лишь увеличивает номер после изменения исходных таблиц. `search_catalog_products` читает текущие `products` с `published = true`, а публичные роли имеют прямой `SELECT` на опубликованные товары и связанные записи. Если подключить сохранение админки, поиск и прямой Data API покажут правку до обновления статических страниц. Проверка номера до/после сборки обнаруживает гонку, но не хранит старое содержимое. Существующий Vercel/Next тоже читает исходные таблицы, поэтому его нельзя оставлять общедоступным источником черновиков.

## Выбранный подход

Текущие таблицы каталога становятся редактируемым **источником** для админки, а отдельный неизменяемый **снимок выпуска** — источником для всех публичных чтений. Снимок включает данные, от которых зависят страницы и публичный поиск: категории, подкатегории, бренды, типы техники, товары, связи, характеристики, медиа-ссылки и витрину техники. Его номер и контрольная сумма записываются в пакет сайта. Снимок не меняется после создания; новую правку можно выпустить только новым снимком.

Отдельный Node-сборщик с серверным, недоступным браузеру ключом читает источник в согласованном состоянии и создаёт закрытый снимок версии `R`. Затем он собирает страницы **из этого снимка**, а не из меняющихся исходных таблиц. Существующие функции страниц получают общий read-only адаптер каталога; в режиме сборки ему передаётся `R`. Админские чтения и записи продолжают использовать источник. Если в источнике появляется более новая ревизия до завершения выпуска, пакет `R` считается устаревшим и не продвигается: очередь начинает новую сборку. Так не публикуется случайная смесь двух редакций.

Для поиска сохраняется публичный маршрут `/rest/v1/rpc/search_catalog_products` и общий `ProductPage`-контракт. Одна сигнатура RPC получает два новых необязательных аргумента — идентификатор выпуска и ограниченное право его чтения; прежний запрос legacy без них остаётся совместимым и читает активный выпуск. Worker передаёт оба аргумента и получает именно свой снимок. Это **не** service-role key. Право хранится только в серверном binding Worker, не попадает в HTML, браузер, URL, логи или пакет файлов. Прямой вызов RPC без этого права может читать только активный публичный выпуск, а не ожидающий снимок. Приватные таблицы снимков не получают прямого `SELECT` для `anon`/`authenticated`; привилегированный SQL-код находится в неэкспонированной схеме, с фиксированным `search_path`, явными `REVOKE`/`GRANT` и проверкой права на конкретный выпуск.

Публичный доступ к редактируемым исходным таблицам и их связям закрывается **только после** того, как Cloudflare и legacy Next/Vercel смогут читать опубликованный снимок. Для legacy это отдельный совместимый адаптер: его публичные страницы/поиск читают активный выпуск, а не черновик. До этого переключения реальные admin-mutations в Cloudflare Worker остаются отключёнными. Ключ администратора никогда не используется в публичном поиске.

Новые медиа сначала попадают в закрытую staging-зону. Опубликованные URL неизменяемы: новый файл получает новый ключ, старый файл не перезаписывается и не удаляется при неудачной сборке. Поэтому старая страница не меняет изображение до выпуска новой версии.

## Последовательность выпуска

1. Админская правка сохраняется в источнике с обычной проверкой конфликта; админка показывает «ожидает публикации». Публичный выпуск пока не меняется.
2. Сборщик фиксирует ревизию `R` и создаёт закрытый снимок. По нему выполняются Next build, crawl, проверка HTML/SEO, sitemap, ссылок, медиа, размера и целостности пакета; затем проверяется, что исходная ревизия всё ещё `R`.
3. Пакет Worker + Static Assets загружается как **неактивная** версия Cloudflare. Предпросмотр версии проверяется с тестовыми/ограниченными bindings. Загрузка сама по себе не меняет публичный домен.
4. После успеха всех ворот снимок помечается доступным только по праву этого выпуска. Затем одним переключением Cloudflare версия Worker вместе со статическими файлами начинает обслуживать посетителей. Worker поиска запрашивает именно её снимок. Отдельный указатель «активный выпуск» для legacy Next и обычных публичных RPC переводится на эту же версию после подтверждения Cloudflare. До переключения и при отказе остаётся прежний выпуск.
5. Очередь подтверждается лишь после проверки живого нового выпуска. Его номер, пакет, контрольные суммы, Cloudflare version/deployment ID и время записываются в журнал выпуска без секретов. Старый пакет и снимок сохраняются для отката.

Cloudflare хранит код, assets и bindings как одну версию; это даёт переключение страниц и Worker вместе. Состояние Supabase и R2 в версию Cloudflare не входит, поэтому данные закрепляются отдельным неизменяемым снимком. Возможный короткий интервал между переключением Cloudflare и указателя legacy безопасен для основного домена: Worker уже закреплён на новом снимке, а legacy продолжает прежний, но полный публичный аудит обоих origin обязателен до cutover.

## Отказ и откат

- Любой сбой до активации Cloudflare оставляет старый публичный пакет и активный снимок без изменений. Кандидат сохраняется только для диагностики, без статуса «готов к production».
- Если активация или проверка живого сайта неуспешна, координатор возвращает прежнюю Cloudflare-версию; старый снимок остаётся доступным. Указатель legacy возвращается на старую версию при необходимости. Повторить выпуск можно только после сверки фактического deployment ID и состояния очереди; неизвестный результат нельзя трактовать как успех.
- Снимки, пакеты и медиа старых выпусков не удаляются автоматическим откатом. Удаление возможно лишь отдельной политикой хранения после подтверждения, что ни один активный или резервный выпуск их не использует.
- Если новая админская правка пришла во время сборки, кандидат устаревает и не активируется. Очередь строит свежую ревизию; админка показывает ожидание, а не ложный успех публикации.

## Проверки перед подключением записи

- SQL/pgTAP + настоящий локальный PostgREST: `anon` не читает черновик ни прямыми таблицами, ни RPC без права; Worker с разрешением получает только свой снимок; ошибки/неверное право закрывают чтение без fallback на источник.
- TDD контракт Worker/legacy: одинаковые `ProductPage`, фильтры, точное количество, пагинация, canonical URL, пустой результат и ошибки для активного выпуска.
- Изолированная сборка на настоящей локальной базе с правкой во время build: отказ без изменения выбранного пакета; успешный пакет показывает новую редакцию на страницах и в поиске, старый пакет — старую.
- Fault injection для каждой границы: создание снимка, build, crawl, upload, активация, проверка live, подтверждение очереди, откат и потерянный ответ. Ни одна ошибка не объявляет `productionReady: true` или успешный выпуск раньше фактического подтверждения.
- Браузерные проверки desktop/mobile и прямые HTTP-запросы к Supabase, Cloudflare staging и legacy-origin. Проверить секреты, заголовки, 404, медиа, ссылки и SEO. Только после этого решать DNS cutover.

## Порядок внедрения и запреты

Сначала локальная модель снимков и безопасное чтение, затем сборщик, Worker и legacy adapter, затем release/rollback coordinator, и только после этого admin mutations. Существующие публичные SQL-права нельзя отнимать на production до совместимого релиза обоих читателей. Не менять production Supabase, Cloudflare, DNS, Vercel, R2 и не делать push на основании одного этого документа. Удалённый staging, Worker Free CPU/quota, DNS-схема и коммерческая пригодность остаются отдельными воротами.

## Отклонённые варианты

- «Сохранить в живую таблицу, потом собрать»: поиск и прямой Data API покажут новую запись раньше страницы.
- Только очередь и `content_revision`: обнаруживают изменения, но не сохраняют старую редакцию.
- Отключить поиск на время сборки: ломает полезное поведение сайта и не закрывает прямое чтение Supabase.
- Отдельная оплачиваемая база/хостинг: не нужен для выбранного бесплатного решения.

## Источники платформенных ограничений

- Cloudflare Workers [Versions & Deployments](https://developers.cloudflare.com/workers/versions-and-deployments/): версия включает код, assets и bindings, но не состояние внешних хранилищ.
- Cloudflare Workers [Static Assets](https://developers.cloudflare.com/workers/static-assets/): Worker и assets загружаются как один deployment.
- Supabase [Database Functions](https://supabase.com/docs/guides/database/functions): права функций и `search_path` для привилегированного SQL.
- Supabase [Securing your API](https://supabase.com/docs/guides/api/securing-your-api): прямые grants и RLS проверяются отдельно.
