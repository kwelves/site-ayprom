# AYPROM — память проекта и руководство для напарника

Дата: 23 сентября 2026 года. Подготовлено Codex для передачи Cursor по прямой просьбе пользователя.

Это полная практическая сводка доступного контекста о проекте и работе с пользователем. Она объединяет договорённости из разговоров, локальную память, документы проекта, Git и результаты проверок. Она не заменяет исходники и не гарантирует, что состояние веток останется таким же после этой даты. Паролей, токенов, ключей API и значений секретных переменных здесь нет.

## 1. Как быть полноценным напарником

Пользователь хочет работать с самостоятельным техническим партнёром: понимать цель, предлагать решения, реализовывать их, замечать риски и проверять результат. Не ограничивайся ролью исполнителя отдельных команд. В пределах выданной задачи доводи работу до проверяемого результата, сохраняй её и ясно объясняй, что получилось.

Сохраняй собственное суждение. Если в задании или отчёте другого агента обнаруживается ошибка, объясни её по коду или тесту и предложи исправление. Не соглашайся автоматически. Более сильный вариант продукта можно предложить, но крупную смену направления нужно согласовать.

У пользователя нет обязанности разбираться во всех инструментах разработки. Он прямо говорил, что большое количество непонятных действий во время миграции вызывает тревогу. Сначала объясняй человеческий результат: что заработает, что проверено, что ещё мешает. Технические подробности добавляй ровно в той мере, в какой они помогают понять решение.

Не обещай «всё без ошибок» после успешной сборки. Честный ответ о границах проверки укрепляет доверие лучше, чем успокаивающее неподтверждённое заявление.

- Он ценит качество, скорость и самостоятельность агентов; разрешил давать внешним агентам серьёзные задачи с реализацией кода.
- В Cursor у него больше доступных лимитов, чем в ChatGPT и Claude. На присланном скриншоте выбран `Claude Fable 5.1 1M High`. Это наблюдаемое название в интерфейсе, а не независимая оценка качества модели.
- Фраза «дай следующую задачу Клоду/Курсору» означает: подготовь готовый промпт для вставки в другой чат. Пользователь сам отправит его агенту и принесёт результат обратно.
- Перед интеграцией пользователь ожидает независимой проверки отчётов по Git, исходникам и тестам.

- Если говорит «стоп», остановись. Если говорит «продолжай», сначала восстанови фактическое состояние и продолжай с сохранённой точки.

Не делай выводов о личности, компетенциях вне обсуждённой темы или биографии по именам каталогов. Других надёжных личных сведений для этой работы не требуется.

## 3. Завершение рабочего дня — явная договорённость

Фразы вроде «на сегодня пока всё, завершаемся», «всё, завершаемся», «на сегодня завершаемся» означают завершение рабочей сессии с сохранением состояния. Пользователь хочет выключить ноутбук, завтра открыть новый чат и написать «давай продолжим незавершённую работу».

Перед завершением:

1. Уточни факты: папка, ветка, HEAD, `git status --short --branch`, свои изменения и незавершённые задачи.
2. Обнови граф знаний по правилам `AGENTS.md`, дождись результата команды.
3. Сохрани понятный локальный Markdown-handoff: что сделано, что проверено, что осталось, точный следующий шаг, ветки/папки других агентов, команды и ограничения.
4. После среднего/крупного завершённого изменения создай локальный Git checkpoint только своих файлов. Не коммить чужую незавершённую работу и не скрывай её.
5. Запиши незавершённые команды и свои фоновые процессы. Завершай только процессы, которыми владеешь и которые безопасно остановить. Общие сервисы не выключай автоматически.
6. Дай короткое подтверждение, где лежит handoff и с чего начнётся следующая сессия.

В Codex дополнительная локальная память хранится в `C:\Users\user\.codex\memories\extensions\ad_hoc\notes\`. Cursor не обязан иметь тот же механизм: сохрани свой handoff в согласованном месте своей рабочей копии и передай путь пользователю. Координатор объединит результаты. Не редактируй глобальные реестры памяти другого агента.

Автоматический плагин `claude-mem` и локальные Markdown-handoff — разные механизмы. Во время этой сессии плагин сообщил о паузе из-за лимита своего провайдера; ручные записи оставались доступны. Позже пользователь подтвердил, что рабочий Claude также упёрся в свои лимиты. Не связывай все сбои памяти с состоянием проекта и не перезапускай сервис памяти ради обхода квоты.

## 4. Что такое AYPROM

AYPROM — каталог запчастей и оборудования для спецтехники и грузовиков с административной частью. Цель посетителя: быстро найти подходящую деталь, открыть её карточку и связаться с компанией.

Фиксированные продуктовые ограничения из `PROJECT_BRIEF.md`:

- Это каталог. В первой версии нет корзины, онлайн-оплаты и checkout.
- Цены не показываются. Наличие также не должно появляться в карточке первой версии лишь потому, что поле существует в БД.
- Данные каталога и административный доступ должны оставаться защищёнными.
- Supabase — источник данных. Production не подменяется захардкоженным демонстрационным каталогом при ошибках.
- Fixture-данные допустимы в изолированных тестах, локальной разработке и проверках производительности.

Каталог рассчитан примерно на 2000 товаров. Поиск и пагинация выполняются на стороне сервера/БД: браузеру передаётся страница, обычно 24 товара. Нельзя загружать весь каталог в браузер ради простого фильтра.

Поиск — основной способ уточнить выбор. Он должен охватывать название, артикул, бренд, категорию и характеристики. AI/семантический поиск не входит в первую версию. Полноценная боковая панель фильтров не является обязательной; небольшие полезные фильтры можно предлагать по реальной потребности.

Аудитория — владельцы техники, механики, водители, операторы и небольшие компании. Важны понятность, визуальное узнавание товара и быстрый контакт. Не добавляй сложные интерфейсы ради демонстрации технологии.

## 7. Договорённости о проверках и Git

Работа по миграции ведётся через TDD: сначала тест на нужное поведение и ожидаемый RED, затем реализация и GREEN. Уже написанный другим агентом код проверяй по истории его RED/GREEN и реальному поведению. Для найденного нового дефекта сначала воспроизведение.

Основные команды:

```text
npm run check
npm run build
npm test -- --maxWorkers=2
npm run test:cloudflare:static-contracts -- --maxWorkers=2
npm run test:cloudflare:postgrest
npm run test:cloudflare:assets
git diff --check
git status --short --branch
graphify update .
```

`npm run check` объединяет lint, typecheck, проверку цветовых токенов и Vitest. Если выполняешь шаги отдельно, так и отчитайся. Успешный запуск тестов — не доказательство production-parity.

При двух одновременных полных Vitest-прогонах были таймауты по 5 секунд в `local-geist-font-contract` и `media-migration-cli`. Оба полных набора прошли с `--maxWorkers=2` без изменения кода и таймаутов. Это конкретно проверенный способ ограничить нагрузку на ноутбук, а не разрешение списывать любые падения на случайность.

Playwright для общих локальных fixtures ранее был ограничен `workers: 1`, чтобы избежать гонок данных. Не путай этот параметр с количеством процессов Vitest.

Для SQL нужны локальные pgTAP и проверки схемы/прав; для маршрутизации — реальные HTTP и браузерные проверки. Не замыкай проверку на mock, который просто повторяет предположение реализации. Пример уже случившейся ошибки: mock принимал POST Range-пагинацию, хотя настоящий PostgREST её игнорировал.

После среднего/крупного изменения: релевантные проверки, Graphify, локальный Git checkpoint с ясным названием. Никакого автоматического push. Пропущенный, прерванный или недоступный тест не считается успешным.

Graphify запускается перед первой работой в новой сессии, если `graphify-out/graph.json` существует: `graphify update .`; без графа используется `/graphify .`. После среднего/крупного изменения граф обновляется перед checkpoint. Это не правило «запускать заново после каждого сообщения». При ошибке сообщи один раз и продолжи по исходникам. Не перестраивай чужой граф параллельно из другой сессии.

## 8. Цель и выбранная архитектура миграции

Цель — перенести хостинг AYPROM с Vercel на Cloudflare, сохранив функции, URL, SEO, безопасность и качество медиа, с учётом бесплатных лимитов. Бесплатность — ограничение архитектуры, а не обещание, что любая нагрузка всегда будет стоить ноль.

Принята схема:

| Компонент | Ответственность |
|---|---|
| Cloudflare Static Assets | Готовые публичные HTML/JS/CSS/шрифты; в будущем оболочка админки |
| Тонкий Worker | API, поиск, пагинация, health; позже redirects/auth/admin API |
| Supabase Postgres | Каталог и другие данные, RLS, публичный search RPC |
| R2 | Медиа |
| Внешний Node build/processor | Sharp и подготовка файлов/сборок |
| Next/Vercel | Рабочий legacy adapter и rollback-origin на период перехода |

Полный vinext runtime не выбран production-основой. Исследовательский spike нашёл проблемы Sharp/stubs, Node-зависимостей, установки и полноты паритета. Он не является готовой системой переноса.

Текущий Worker-first охватывает `/api/*`. Публичный просмотр должен обслуживаться Static Assets без обязательного выполнения Worker на каждой странице. Auth и admin-first routing пока не реализуются.

Текущая production-авторизация по последней проверке использует `ADMIN_PASSWORD`; таблица `admin_credentials` была пуста. Это историческое наблюдение, не свежий запрос к production. Не начинай перенос auth по старому предположению о Supabase Auth или заполненной таблице паролей.

## 9. Статическая сборка: crawl-and-freeze

Выбран внешний Node builder. Он запускает локальный Next, получает HTML публичных маршрутов по заранее сформированному manifest, собирает допустимые assets, проверяет результат и лишь затем готовит статический артефакт.

Полная спецификация: `docs/superpowers/specs/2026-09-21-ayprom-crawl-and-freeze-design.md`.

Ключевые решения:

- Route manifest строится из зафиксированного snapshot данных. Sitemap и ссылки используются для сверки, а не как единственный источник списка маршрутов.
- Есть режимы fixture и local snapshot. Unrevisioned production crawl не считается воспроизводимой релизной сборкой.
- Public reads только с публичным ключом; service-role не нужен ни для поиска, ни для построения списка публичных страниц.
- Preflight проверяет origins, режим, ключи, SHA, выходные пути и другие предпосылки до создания/замены итогового сайта.
- Сначала staging под `dist/`; предыдущий успешный `dist/site` сохраняется при любой ошибке.
- Корень → `index.html`; остальные страницы → `<route>.html`. Это позволяет иметь одновременно файл категории и вложенные страницы.
- `dist/site/` — будущий загружаемый артефакт, `dist/meta/` — внутренние отчёты вне Assets directory.
- Копируется `.next/static`; из public берутся только нужные tracked-файлы. Широкое копирование public и untracked запрещено.
- Запрещены секреты, `.env`, source maps, исходники, node_modules, Markdown, RSC-файлы, локальное видео и `/_next/image` в итоговом артефакте.
- Спецификация содержит лимиты и проверки количества/размеров файлов; актуальные тарифные ограничения проверяются ещё раз перед выпуском.
- В статическом режиме поиск/страницы после первой получают данные через API. Клиентский adapter с back/forward, ошибками и loading ещё предстоит завершить.
- Next RSC/navigation и prefetch надо проверить в браузере на workerd. Если нужны обычные document navigation links, делаем это в отдельном static-build режиме.
- Product aliases `/product/<slug>` сохраняются в manifest как pending для последующего Worker redirects slice; не раздуваем `_redirects` и не объявляем их runtime-паритет готовым.

## 11. Контракт поиска и известные тонкости

Публичный RPC: `search_catalog_products`. В существующем контракте пять аргументов: `search_query`, `category_filter`, `subcategory_filter`, `brand_filter`, `vehicle_type_filter`.

`ProductPage` содержит `items`, `total`, `page`, `pageSize`, `totalPages`. Сохраняй точный shape и семантику обоих adapters, в том числе явные undefined-поля JS-объектов там, где это часть существующего результата. HTTP JSON естественно не содержит undefined.

Для POST RPC PostgREST игнорирует Range header: нужны URL-параметры offset/limit. Корректный HTTP 416 с `Content-Range: */N` при запросе после конца результата должен обрабатываться согласно общему контракту; Worker уже возвращает пустую страницу с total N. Точное поведение legacy SDK на 416 нужно проверить отдельно настоящим HTTP: ранее отмечалось возможное несовпадение. Нельзя объявлять parity только по успешным страницам и mock-ответам.

Публичному поиску запрещён service-role. Ошибки Supabase в Worker возвращаются в обезличенном виде, без тел внутренних ошибок и секретов.

Смешанная категория содержит карточки подкатегорий и прямые товары с `subcategory_id IS NULL`. `subcategory_filter = NULL` в старом RPC означает «все подкатегории», поэтому для прямых товаров понадобился отдельный явный флаг.
